Research Report · 2026-09-15 · for James, before building the replay expander

Gods of the Arena replay format and a replay-expander design

For James, before we assemble the Gods of the Arena replay expander. The research used Metta-AI/polyworld commit 5422fb0c, the commit of the live game. Polyworld main (1d7eb723) is different from that commit and is not a valid re-simulation target (section 3).

Executive Summary

A hosted Gods of the Arena replay is not a record of game state. It is a binary action tape. The tape has a short header and the match setup (seed, map hash, ten heroes with team, seat, lane and class). It has the hosted match configuration with the public player display names. It has each BASIC action call as a 20-byte record and one state hash for each tick. It also has CPU samples for each second (1, 2). The file has nothing else: no positions, no HP, no gold, no kills, and no damage. A 60-line pure-Python decoder from this investigation reads a real league replay to the last byte. The last recorded hash is equal to the hash: line in the game log of that episode.

Only re-simulation can recover all other data. Playback operates the full engine again and applies the recorded requests through the same validators. It compares the state hash on each tick (3, 3). This is correct only at the exact source commit that recorded the game. A build at polyworld main moves away from the sample replay at tick 132. A build at 5422fb0c re-simulates all 28,800 ticks with zero mismatches in 24 seconds on this arm64 Mac, and it reproduces the hosted game log exactly. The manifest of the coworld gives the correct commit, thus no guess is necessary. The proposed expander has the same shape as the Crewrift and Heartleaf tools. Layer A is a small Nim program in our repo, compiled against the polyworld tree that we fetch. It writes JSONL events and sampled state. The Python tape decoder is the fallback when no build is possible, and Python statistics, compare.py and features.py adapters sit on top. The main open design decision is damage attribution. The engine never records damage, thus we must apply a one-line simulator patch or accept a first version with victim-side data only.

Each item marked verified was compared with the polyworld source at 5422fb0c, with a real league replay from the Observatory, or with both. Inferred items come from the source but were not exercised.

1 · Where replays come from

  • The hosted game records an action tape in memory during the match and writes it one time at the end (verified).
  • Each completed episode has a replay, because the game does not publish results without one.
  • The Observatory serves the raw bytes from public S3 and through the episode-artifacts route. The shared downloader saves them with the name replay.json, but the file is binary.

The hosted game operates the headless polyworld binary, compiled with -d:coworld. The runner gives the output path in COGAME_SAVE_REPLAY_URI (4). The game makes a recorder for each match together with the current setup, and it copies the hosted GotaConfig into the tape (5). At the end of the match, saveRecording calls saveReplay (5, 2). If the replay file does not exist, finishCoworld does not publish the results (4). Thus each completed episode has a replay.

The Observatory serves the file in two ways, and both were verified on the sample episode. episode.json.replay_url points at https://softmax-public.s3.amazonaws.com/replays/<job>.replay, on public S3, as raw bytes. The manifest declares replay_viewer.replay_compression: "gzip", and the inspector of polyworld accepts a gzip prefix (6). But the bytes we received were not compressed. The second route is /v2/episode-requests/{id}/artifacts/replay, which the shared fetch_artifacts.py uses. That script saved 6,119,872 identical bytes as replay.json.z and as replay.json, because its zlib step fails silently and then keeps the raw blob. The file with the name replay.json is not JSON. Use it as replay.bin.

2 · The file format

  • A hand-written header (magic, format version, game version, game name) comes first. Then a Flatty serialization of one Nim object comes (verified).
  • There is no compression, no state for each tick, and no event log.
  • Each action has 20 bytes. There are 14 action kinds, and BASIC policies write at most 12 of them.

A GotA replay is the generic polyworld tape container (1). A small header comes first, then a Flatty (0.4.0, -d:flatty64) serialization of ActionTape[Setup, ReplayAction, ReplayMetrics, GotaConfig]. Flatty writes object fields in declaration order. The lengths of int and seq values are 8-byte little-endian, enums are 8 bytes, and a bool is 1 byte. A seq of a plain-data object is a raw copy of the Nim struct, with the padding (7).

A pure-Python decoder of this layout reads the sample replay and the in-repo examples/gods_of_the_arena/replays/demo.replay to the exact last byte. The last entry of hashes (0x320ad325) is equal to the hash: line in the game_logs.log of the episode. The prototype, gota_replay_probe.py in the scratchpad of this session, has approximately 60 lines of struct calls. Move it into the lab as it is. Appendix A shows the decoded header of the sample.

config.players[].name is the public player display name. Thus the replay itself tells you who sat where. Hero id 100 + slot is seat 0–4 (Red), and 105 + slot is seat 5–9 (Blue). episode.json.participants[].position uses the same order.

3 · Playback and version coupling

  • The tape stores requests. The engine records each request before it accepts or rejects it. Playback operates the full simulation again and compares the hash on each tick (verified).
  • The recorded game version (33) does not identify a compatible build. The source commit does, and the coworld manifest gives it.
  • An arm64 host build reproduced the hosted game exactly on the one sample. Keep the hash check as the guard.

The engine records each BASIC action call before it examines the call (13). Playback operates the simulation again and applies the recorded requests at their ticks through the same validators (applyReplayAction, 3, called from tickWorld, 3). On each tick it compares stateHash with the recorded hash (3). This is the same design as the bitworld .bitreplay of Crewrift and Heartleaf. Thus all that the Crewrift replay notes say about version coupling (14) applies here.

ReplayGameVersion (33) is not sufficient to select a compatible simulator. A build at polyworld main (1d7eb723, also version 33) moves away from the sample replay at tick 132, with 28,669 mismatches. The in-repo demo.replay also moves away, at tick 135. Three changes to the simulation (tower collision, creep lane resume, creep upscale) were merged after the live build without a version increase. A build at 5422fb0c re-simulates both replays with zero mismatches on this arm64 Mac. The headless summary reproduces the hosted game log exactly:

result: time limit
forts: red 400 hp, blue 400 hp / towers: red 4, blue 5
hash: 00000000320AD325 map 0000000029424656
heroes: red L13 L13 L8 L3 L12, blue L10 L10 L9 L10 L9
economy: red 21200 XP / 635 gold, blue 18950 XP / 680 gold
replay: 291325/291325 actions          (24 s wall clock for 28,800 ticks)

Two results come from this. First, the correct ref is not a guess. GET /v2/coworlds/{coworld_id} returns manifest.game.runnable.source_url in the form https://github.com/Metta-AI/polyworld/tree/<sha>/coworld/gota. The build script must get GOTA_REF from that, with episode.json.coworld_version as the cache key. This is the same as the current CREWRIFT_REF and HEARTLEAF_REF pins, but automatic. The policy of polyworld is that older replays use their archived client and that no compatibility branches are added (2). Also, replays.nim has 12 commits in five days. Thus expect frequent re-pins. Second, arm64 host builds are sufficiently deterministic. Map generation uses float32 presets, but the map hash and all 28,800 tick hashes matched, and validateReplayWorld (3) passed. No Docker or amd64 build is necessary for expansion. This is one sample. Keep the hash check as the guard. Appendix B gives the build recipe that worked.

4 · The other artifacts of an episode

  • results.json and game_logs.log give the outcome, the levels, the team XP and gold, the tower counts and the VM status. The replay is not necessary for these.
  • The private log of each seat has each PRINT and each BASIC error, but only for the seats that the current identity owns.
  • GotA makes no player artifact ZIP.
File Content
results.json {"scores":[10 × 0/1],"ticks":28800,"seed":…,"outcome":…,"banked_gold":[],"returned":[],"total_xp":[10 ints]} where outcome is one of time_limit, RedTeam, BlueTeam (15, 4). banked_gold and returned are fields from a different game and are always empty for GotA.
game_logs.log Container stdout. The game section is the headless summary: replay saved … (N actions), result, forts, towers, hash, heroes (levels), economy (team XP and unspent gold), scripts: 10/10 active, N decisions (5). This is a cheap end-of-game signal. scripts: 10/10 active tells you if a VM stopped.
Private log of each seat Only for the seats you own. It has Player slot N started., each BASIC PRINT, BASIC error: … on VM failure, and Player slot N completed.. The limit is 10 MiB (4). It has no tick stamps unless the policy prints worldTick. The route is /v2/episode-requests/{id}/{policy_version_id}/policy-logs/{position}. On the sample episode, the games-bond-gota seat returned 403 You do not own this policy with the login in use at that time. That policy belongs to the "Games Bond" player identity (see the coworld-player-swap skill).
Player artifact ZIP GotA does not make one (integration.md: "No player artifact ZIP is produced").
episode.json Discovery row: participants[] {position, policy_name, version, policy_version_id, player_name, is_filler}, participant_scores, coworld_version, replay_url, inspect_url.

5 · What is recorded and what is recoverable

  • Directly from the file: each action request with its tick and hero, the CPU of each seat for each second, and the episode setup.
  • With re-simulation: the complete world state on each tick, with the automatic casts of the engine and the team vision.
  • The reward arithmetic is exact at the hit site. Thus last hits and tower kills are attributable on each tick.

5.1 Directly in the file (no re-simulation)

For each action, accepted or not, the file has the tick, the hero id, the kind and the arguments. That gives command rates, target selections (object ids only, no positions), shop requests, item-use requests, and cast requests. It also gives the last tick on which the VM of each hero made calls, because a VM that stopped is not in the file after that tick. For each second and each seat, metrics.frames gives the CPU percentage (instructions used, divided by the budget of 20,000). metrics.final gives the average for the full game. A value of -1 means no VM, that is, a human seat. For each episode, the file has the seed, the map preset, the hero roster (id, team, slot, lane, class), the player display names, the recorded duration (len(hashes)) and the creation time. The file does not have: acceptance of an action, positions, HP, gold, XP, level, kills, deaths, damage, item inventories, ability charges, structure HP, or fog.

The reward arithmetic is exact and attributable at the hit site (applyHeroHit, 3). A footman kill gives +25 XP and +15 gold, a hero kill +150 and +100, and a tower kill +100 and +75 (3). Fort damage gives nothing. Spell strikes go through the same procedure (hitSpellTarget, 3), thus spell kills are credited. Tower and footman damage to heroes calls hitHero(-1, …) (3, 3). That records a death with no killer seat.

5.3 Prior art in polyworld (verified)

Polyworld has a minimal re-simulation extractor for its tournament tool: inspectReplay in 6 and 16. It plays the tape, rejects each hash mismatch, and compares scores() with participant_scores. Then it writes end-of-game JSON for each seat: hero, class, team, win, draw, level, xp, xp_progress, gold (earned), banked_gold, kills, deaths, assists. From the exact reward arithmetic, it then computes tower_kills and last_hits (objectiveCounts, 17). It gives only the end state, with no timeline, positions or events. It also imports curly, zippy and jsony for the tournament runner. Copy its loop. Do not make it a dependency.

6 · What is not recorded

  • Without a version-matched re-simulation, only command counts are available.
  • The tape has requests, not effects. Damage and healing totals exist nowhere.

  • Automatic casts, visibility and policy reasons are derivable or private. They are never recorded.

  • No state for each tick in the file. All data other than command counts is necessary from the version-matched re-simulation of section 3. If a ref cannot be built (a source commit that no longer exists, or a private dependency change), only the action stream of the replay is readable.

  • Requests, not effects. attackTarget(id) in the tape does not mean that the hero hit that target, or that the hero moved to it. Acceptance must be computed again (applyReplayAction returns the accepted flag), and the effect must be read from the world state after that.
  • No damage or healing totals. GotA never writes DamageMetric, HealingMetric, ArmyMetric, BankedMetric or StructuresMetric (grep of examples/gods_of_the_arena/*.nim). The report of polyworld says "Damage and healing totals are not tracked … and are not reported as zero". A hook on applyHeroHit in the expander can recover them easily, but the file and the stock tools do not have them.
  • No attribution for each hit from a tower or a creep. hitHero(-1, …) records a hero death from a non-hero source, without a tower or footman tag. The expander sees the call site, thus it can add the tag.
  • Automatic ability casts are not in the tape. They occur inside updateHero → tryCastAbility. Only world.casts during re-simulation has them.
  • No policy-side reasons. PRINT output is private to the owner of the seat, and only for the seats you own. The logic of other entrants is not visible. For our own seats, the private log is the only "why" channel, and it has no tick stamps unless the policy prints worldTick.
  • No wall-clock or schedule data, other than createdUnixMs.
  • Visibility is derivable, but it is not recorded. To know if an enemy was visible to a hero on a tick, compute it again from teamVisible. The tape does not say what the script saw.
  • Tool mismatch in the shared downloader. fetch_artifacts.py gives the binary tape the name replay.json. A tool that expects JSON fails. A test for the POLYWORLDREPLAY magic, or a game adapter hook, is necessary.

7 · Proposed expander design

  • Three layers, with the same pattern as Crewrift and Heartleaf: a Nim re-simulation expander, a pure-Python tape decoder, and Python analysis on top.
  • The expander is our file, compiled against the polyworld ref that the build script fetches. Thus a renamed field is a compile error, not silent wrong data.
  • The events come from a comparison of the world state between ticks. Damage attribution is a stub until the engine records it (change request 6).

7.1 Shape

Layer B exists as a prototype (the 60-line struct decoder) and never needs a new build. It is the fallback when a ref does not build, and it is sufficient for command-rate, shop and target-policy questions. Layer A gives the value. Layer C is plain Python on JSONL or Parquet. This is the same as the crewrift-event-warehouse pattern and the Heartleaf replay visualizer (18).

The module layout is the same as heartleaf_lab/tools/:

gods_of_the_arena_lab/
  tools/
    build_expand_replay.sh      # resolves GOTA_REF from /v2/coworlds/{id} (cache by coworld_version),
                                #   tarball fetch, nimby sync, host-native nim c; caches bin/expand_replay-<ref>
    expand_replay.nim           # OUR file, compiled against the fetched polyworld tree (see 7.2)
    bin/expand_replay-<ref>     # gitignored
    replay_actions.py           # layer B: pure-Python tape decoder (lifted from the prototype)
    replay_stats.py             # layer C: expanded.jsonl -> per-hero / per-team tables (markdown + JSON)
    viz_replay.py               # layer C: paths / heatmaps on the tile grid (Pillow, like heartleaf's)
  .claude/skills/gota-ab/scripts/compare.py                # coworld-ab adapter
  .claude/skills/gota-hypothesis-miner/scripts/features.py # miner adapter
  docs/replay-format.md         # the reference once the tools exist

expand_replay.nim is in our repo, because polyworld has no such tool. We compile it with the polyworld source on the --path. It imports polyworld/[tapes, metrics] and examples/gods_of_the_arena/[content, maps, replays, sim], exactly as herostats.nim does. The file stays at approximately 300 lines: the herostats.nim loop, the output for each tick, and some event detectors that compare states. The build script fetches a ref, and the file compiles against that ref. Thus the file obeys the one-client-per-gameplay-version rule of polyworld automatically. If a future polyworld commit renames a field, we get a compile error and not silent wrong data.

7.2 Expander core loop (inferred from herostats.nim, not yet written)

let data = decodeReplay(bytes)                       # gzip sniff like herostats
let game = newGame(generateMap(data.config.seed, data.config.mapPreset),
                   data.config.spawnIntervalTicks, 0, true, data)
game.replayPlayer = initReplayPlayer(data); game.historyPlayback = true
emit meta row
while game.world.tick < data.hashes.len:
  snapshot previous world (clone or copy the fields we diff)
  game.tickWorld(nil)                                 # applies tape actions, checks hash
  diff previous vs current -> events; every N ticks -> state rows
require game.hashCheck.mismatches == 0 (else summary.hash_failed = true, exit non-zero)
emit summary row

The events come from a comparison of the state between ticks. No engine change is necessary:

Event Detection Fields
action Each tape action consumed this tick, with the applyReplayAction result slot, kind, args, accepted. This needs a call to the validators from our code, or the game.metrics command delta. The simplest method: consume the actions in our loop and call applyReplayAction directly, as the branch in tickWorld does
hero_death, hero_respawn hp > 0 → ≤ 0 (state Dying), then hp above 0 again at spawn slot, tick, pos, killer_slot (from the stats.values[KillsMetric] delta on that tick; -1 if tower or creep)
hero_kill, assist KillsMetric and AssistsMetric delta for each seat
last_hit (footman), tower_kill XP and gold delta, decomposed with the exact reward table (25/15, 150/100, 100/75). This is the arithmetic of objectiveCounts, but for each tick, thus without ambiguity slot, kind, tick
tower_destroyed, fort_damaged, fort_destroyed Tower and fort HP transitions team, lane, tier, tick
level_up level delta
gold_spent, item_bought, item_used Inventory diff and gold decrease on the tick of an accepted buyItem or useItem slot, item, cost
cast New entry in world.casts slot, ability, slot_index, target or point, auto (not in tape at that tick) or explicit
damage Stub until change request 6 lands. The engine keeps no per-hit record, so a comparison of states cannot give the attacker, and the expander must not patch the simulator to get it. Emit damage as a placeholder event type with no rows, blocked on requested game change 6 (damage and heal events in the recording, see gods_of_the_arena_lab/docs/requested-game-changes.md). The hp delta of the victim on each tick is still available through objective_state. Fill this row in as soon as the change ships. tick, source, target, amount, cause (reserved)
objective_state (sampled) On each --snapshot-every N ticks: all hero rows (pos, hp, mana, gold, level, state, target ids, inventory, cooldowns), tower and fort HP, footman counts for each lane and team The feed for positions and heatmaps
visibility (sampled) For each hero: the count of visible enemy heroes and exposed enemy structures Answers "did it attack a target that it saw"

Output contract: one JSON object on each line, with type in meta | action | event | state | summary, and all with tick. Seat-tagged rows have slot (platform seat 0–9, equal to the hero index) and hero_id. Positions are in tile units (mapCoordinate) and also in raw world units. Thus they agree with what BASIC sees and with the terrain* grid. These are the same conventions as the Heartleaf rows (meta, tick, event, summary), thus viz_replay.py is almost a copy.

7.3 Stats tables (layer C)

For each hero, one row for each seat in each episode. The columns are those that the tournament of polyworld defines, plus the columns that only a timeline gives:

slot, team, class, policy_name, version, player, win, draw, level, total_xp, gold_earned, gold_unspent, kills, deaths, assists, last_hits, tower_kills, damage_taken, first_death_tick, time_dead_ticks, first_tower_kill_tick, first_fort_hit_tick, apm, cpu_pct, vm_failed_tick, actions_by_kind{…}, casts_explicit, casts_auto, items_bought{…}, ticks_in_enemy_half, mean_distance_to_nearest_ally, …

For each team: towers_lost_by_lane, fort_hp_min, first_tower_kill_tick, first_fort_hit_tick, hero_kills, hero_deaths, xp, gold, outcome.

For each episode: outcome, ticks, minutes, coworld_version, replay_ref, hash_verified, seed, map_seed.

7.4 Slotting into the shared adapters

The coworld-ab adapter (compare.py) needs only results.json and episode.json for the headline metrics: win from participant_scores, total_xp[position], and outcome == time_limit as the draw rate. by_group must be {red, blue} at minimum, and possibly {class}. GotA fixes the class for each seat (seat 0 is always Death Knight, and so on). Thus the seats that a policy gets have an effect on its numbers, and a group for each class is the honest split (RedHeroClasses, 12, and BlueHeroClasses, 12). The timeline metrics (first_tower_kill_tick, deaths, last_hits) come from the replay_stats.py output, joined on (episode_id, position). The adapter must accept an optional --expanded DIR and use results-only metrics when that is absent.

The coworld-hypothesis-miner adapter (features.py) writes one row for each (episode, own seat). The features come directly from the table for each hero: the "never happened = LAST_TICK+1" rule for timings (first_death_tick, first_tower_kill_tick, first_fort_hit_tick), presence flags (bought_X, cast_ultimate), and counts (last_hits, deaths_to_towers). The score is the total_xp of the seat minus the time penalty of the ladder (100 XP for each simulated minute, per polyworld USAGE.md), or the plain win. Select the score for each question.

If we collect many episodes, the Crewrift event-warehouse pattern (Parquet and DuckDB) applies without change. The JSONL of the expander is its input.

7.5 Cost

Expansion takes approximately 24 seconds for each 20-minute episode on this machine, on one thread. The simulation operates at 49 times real time. A 20-episode experience request expands in less than one minute with four workers. The simulator has module-level globals. This is why herostats.nim operates one process for each replay. Do the same.

8 · Open questions

  1. Ref resolution for old episodes. /v2/coworlds/{id} gives the source commit of the current version. For an episode with an earlier coworld_version, we need a map from version to commit. Polyworld keeps receipts in coworld/releases/*.json (source_commit), but only for some releases, and not for 2026.9.15.1 yet. Keep a local cache of (coworld_version → sha) as we see them, and stop with a clear error in the other cases.
  2. Damage attribution is blocked on requested game change 6: damage and heal events recorded by the engine. Until then damage is a stub, and features.py must not use "damage dealt".
  3. The Nim expander is necessary for the first iteration (decided 2026-09-15). Layer B alone gives aggregates and action requests without acceptance, and that is not sufficient. The expander must also write, per tick and per bot, what that bot could see under fog of war (the team visibility map and the filtered object list), so we know what each policy knew when it acted.
  4. Private logs of our own seats. The "Games Bond" player identity owns the games-bond-gota seat. The login in use during the investigation was not that identity (403 "You do not own this policy"). The James Botts player session that became active later in this session is a different identity again. Before we depend on PRINT traces, make sure that we know which identity owns the policy that we will iterate on.
  5. Downloader name. Change fetch_artifacts.py so that it tests for the POLYWORLDREPLAY magic and saves the file as replay.bin. The alternative is to keep replay.json and document it. This is a small change to a shared skill. It needs a go-ahead because it touches root tools.
  6. arm64 determinism is verified on one episode. Keep the hash check mandatory. If a mismatch occurs with the correct ref, that is the signal to use a linux/amd64 container build instead.

Appendix B: Build recipe

No credentials are necessary. nim 2.2.6 and nimby are already in ~/.local/bin.

curl -fsSL https://github.com/Metta-AI/polyworld/archive/$REF.tar.gz | tar xz -C src --strip-components=1
cd src && nimby --global sync nimby.lock          # writes nim.cfg with dependency paths
nim c -d:headless -d:release --out:../gota_headless examples/gods_of_the_arena/gota.nim
../gota_headless --replay replay.bin              # hash-checked; non-zero exit on divergence
