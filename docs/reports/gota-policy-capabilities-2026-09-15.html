Research Report · 2026-09-15 · for James, before writing the first James Botts policy

What a Gods of the Arena policy can know and do

Researched against Metta-AI/polyworld main as of 1d7eb723. The league currently runs commit 5422fb0c (the coworld manifest's source_url). In the files cited here, the only difference between the two commits is a movement and tower-collision change in the simulation module (git diff 5422fb0c 1d7eb723 -- examples/gods_of_the_arena/sim.nim). Thus every observation, action, and language claim below holds for the live build. Line numbers cite 1d7eb723.

Executive Summary

A Gods of the Arena policy is one plain-text BASIC file. The game compiles it once and then operates it once per simulation tick for each of your five heroes, in five isolated virtual machines. The dialect is small by design: 32-bit integers, IF and WHILE, subroutines without return values, fixed arrays, and PRINT. There is no FOR, no GOTO, no functions, no random numbers, and no strings outside PRINT. Each decision gets 20,000 instructions and 50,000 work units. If a decision uses more than either budget, that hero is disabled for the rest of the match1.

The hero sees a snapshot. It has 13 self fields, six inventory slots, and four ability slots (charges, cooldown, recharge). It also has a list of objects, frozen once per tick: every allied object, plus every enemy object inside your team's fog-of-war vision (id, kind, team, class, x, y, hp, alive). Static terrain is readable through fog. The hero can do six things: walkTo, attackTarget, buyItem, useItem, castTarget, and castPoint. Each call returns accepted or rejected. Three facts shape everything downstream. First, the engine continues to act between decisions. It chases an accepted attack target on its own, an idle hero acquires nearby enemy footmen on its own (never heroes or structures), and it casts abilities on its own in combat with no off switch2. Second, walkTo always clears the attack target, even when the request fails2. Third, the alive flag on towers and forts encodes exposure (attackable now), not whether the structure is still up2. Memory across ticks lives only in the globals and arrays that you declare. As a result, a record of last-seen enemies and plan state is the main lever a policy has over the starter.

1 · The language, exactly

  • Signed 32-bit integers only. true and false are the constants 1 and 0.
  • Statements: assignment, DIM, IF … THEN … [ELSE …] END IF, WHILE … WEND, SUB … END SUB, CALL, RETURN, EXIT SUB, PRINT, END, STOP, REM.
  • Not present: FOR/NEXT, GOTO/GOSUB (reserved words, no implementation), ELSEIF, single-line IF, SELECT CASE, FUNCTION, ABS/MIN/MAX/SQR/RND, string variables.

Polyworld has its own BASIC compiler and register-machine interpreter, written in Nim3. The reserved-word list is the entire grammar surface: and call dim else end exit false gosub goto if let mod not or print rem return stop sub then true wend while xor3. The statement dispatcher has branches for dim, if, while, print, return, exit, stop, end, rem, call, let, assignment, and a subroutine call. It has no other branches3. Thus goto and gosub are reserved, so you cannot use them as names, but no code path compiles them.

FeatureBehaviorSource
ValuesSigned 32-bit integers that wrap on overflow. A positive literal above 2,147,483,647 is a compile error.3
Operators+ - * / MOD, unary minus, = <> < <= > >=, AND OR XOR NOT. Integer division truncates. Division by zero is a runtime error. Both operands of AND and OR always evaluate (no short circuit).3
VariablesGlobal scalars, made on first use, with initial value 0 and case-insensitive names. A variable that gets a value inside a SUB is still global. At most 256 globals.1
ArraysDIM name(N) at top level only, literal bound, inclusive: DIM a(9) holds ten values. At most 32 arrays and 4,096 elements in total. Out-of-range index is a runtime error.3 1
Control flowMulti-line IF cond THEN newline … END IF, with optional ELSE. WHILE cond newline … WEND. Nesting depth at most 32.3 1
SubroutinesSUB name(p1, p2) … END SUB, declared only at top level, called as name(args) or CALL name(args). Parameters are local to the call. At most 16 per routine, 64 routines, and call depth 16. A subroutine in an expression is a compile error: "subroutines do not return expression values".3 1
TerminationThe end of the source, END, or STOP stops this tick's decision. The next tick restarts at line one with globals and arrays intact.3 1
LoggingPRINT "text"; expr, expr: a semicolon joins, a comma inserts a space, a trailing semicolon suppresses the newline. At most 1,024 bytes and 128 print events per decision. Output goes to the private player log.3 1

2 · Execution model

  • One file controls one hero, and every seat gets its own VM with no shared memory. Whether your file fills all five seats of a team (mono-team) or shares a team with the files of other players (mixed-team) is a platform roster setting, not an engine rule.
  • Each living hero's script runs once per tick, 24 ticks per simulated second, in a rotating seat order.
  • Self data is a snapshot taken before the decision. The object list is frozen at the first query in that decision.
  • The engine continues to act between decisions: chase and auto-attack the accepted target, auto-acquire idle enemy footmen, and auto-cast abilities in combat.

Seats 0–4 are Red and 5–9 Blue. loadBots takes one source file per seat and makes an independent runtime for each hero1. The platform decides which player's file sits in which seat, so an ally can be the policy of another entrant. Either way, the only cross-hero information a script has is what it can see about its allies in the object list. Every tick, runBotDecisions goes through the seats from a rotating offset and calls runHeroScript for each one1. That procedure skips dead heroes and heroes whose VM failed. For the others it restarts the runtime, writes the 13 self values, operates the program, and records the instruction and work usage1. A BasicError (a runtime fault or an exhausted budget) sets vm.failed for the rest of that episode1.

Between decisions, the simulation moves the hero along its path, attacks the accepted target, and selects new targets on its own. Every tick, updateHero checks the current attack target again for team, life, vision, and structure exposure. If any check fails, it drops the target without a message2. A hero with no target and no move destination acquires the nearest enemy footman that it can see inside acquireRadius. That radius is 2.5 tiles for melee classes and the basic attack range for ranged classes2. The call passes creepsOnly = true, so an idle hero never locks onto an enemy hero, tower, or fort2. In combat, tryCombatAbilities casts the passive, then the first ready slot among ultimate, secondary, and primary. The one exception is human manual-spell mode, and BASIC cannot turn that mode on2 1.

3 · Observations

  • All coordinates are map tiles in 0 … mapWidth-1. The host converts from 60,000 world units per tile.
  • The object list holds all allied objects plus enemy objects on tiles your team currently sees. Enemies out of vision are absent, not stale.
  • Maximum HP of other objects, XP, enemy cooldowns, projectiles, and any last-seen memory are not exposed.

3.2 Visible objects

objectCount() returns the length of this hero's list of objects, after the visibility filter. The index goes from 0 to objectCount()-1. The host makes the list once per hero per tick, at the first query, and then uses it again for the rest of the decision2. The order is forts, towers, heroes, footmen2. An object is in the list when it is on your team, or when its position is on a tile that your team can see now2. Your own hero is in the list. For an invalid index, every field returns 0, except class, which returns -11.

The whole team shares one vision map, and terrain and structures block it2. Each living hero reveals a radius of 10 tiles, each footman 5, each tower its attack range plus 2, and each fort 142. The object list does not include an object's level, mana, gold, inventory, cooldowns, facing, current target, or movement vector. It does not include spell projectiles or area warnings. It does not include the tower tier or the lane label, so derive those from position.

4 · Actions

  • Six calls, and each returns 1 for accepted or 0 for rejected. Acceptance checks your state, the target's identity, and for walkTo whether a path exists. It does not check whether the action will reach its goal.
  • The host writes every call to the replay before it evaluates acceptance1.
  • walkTo always clears the attack target. attackTarget cancels the walk destination when the target changes.

BASIC cannot do these things: attack-move, sell items, turn automatic spells on or off, send messages between your five heroes, get random numbers, or read any clock other than worldTick. The engine has applyAttackMove2, but the host layer does not register it1.

5 · Consequences for policy design

  • Memory is the main advantage over the starter, because everything the host gives you is a snapshot.
  • Budget one walkTo per tick and read the object list once.
  • attackTarget stays set until something clears it, and walkTo clears it. Do not alternate the two every tick.
  • The alive flag of a structure is a target hint. Track tower HP to know the lane state.
  • The automatic cast will spend the ultimate on a footman. The only lever is to stay out of engine combat until you want it.

Arrays indexed by object ID or class are the only way to keep last-seen enemy positions, threat over time, or plan state across ticks. A hero can see the positions and HP of its four allies. Thus formation logic must be a set of "where are my allies" rules, not messages.

A read of all eight fields for about 40 objects costs about 1,300 work units, well inside the 50,000 budget. But a nested loop over objects × objects, or a terrain sweep, can reach the 20,000-instruction cap and disable the hero for the rest of the match. One walkTo costs 800 units, so about 60 walks fit in a tick. There is no reason to send more than one.

A retreat is one walkTo. To fight again, call attackTarget again. The engine also acquires footmen on its own when the hero is idle, so "stand still and wait" is not a neutral state for a melee hero2.

If a policy wants to keep the ultimate for a hero fight, it must stay out of engine combat until the moment it wants to cast. That means no attack target and no idle footman acquisition, so keep a walk destination. Then call castTarget before attackTarget. The order matters because the automatic cast operates inside the combat update, which comes after the decision.

A purchase has no position condition, so gold must never sit idle. The starter already buys in the middle of a fight8.
