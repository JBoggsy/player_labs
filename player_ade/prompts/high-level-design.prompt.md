# Player Agentic Development High-Level Design Prompt

## Overview
In this session, we're going to develop a high-level design for upgrading this multi-game policy development and improvement lab setup into a webUI-based agentic development environment. We will be working in the `player_ade` subdirectory, which is where we'll store designs, plans, working knowledge, and implemented code. The overarching aim of this project is three-fold: 
  1. significantly improve my experience developing and improving policies with coding agents,
  2. upgrade the existing general-purpose/game-agnostic tools, skills, and knowledge, and
  2. enable parallel long-running agentic tasks by providing both the harnessing and UI/UX for me to interact with them.

### Player-ADE Vision
The 1,000-yard view of my vision for the Player Agentic Development Environment is a system which allows a human -- hereafter called the "user" -- to work smoothly with a coding agent-powered system --hereafter the "player" -- in order to develop policies for coworlds. The core idea here is enabling collaboration between the human user and the coding agent player, so that the player has teh skills, knowledge, and tools it needs both for policy development & improvement and for interacting with the user, and so that the user has observability into the knowledge, actions, beliefs, and strategies of the player and can both direct the player and respond to the player's needs, actions, and questions. There are a few major components to this:
  * a wiki-like solution for recording and discussing accumulated semantic knowledge that allows the both the user and the player to have a complete, shared understanding of that knowledge and allows each to modify that knowledge in a way that's visible to the other
  * a complete idea/experiment lifecycle which allows the user or player to generate ideas, then allows the player to perform and record experiments, results, relevant data, etc. in a way that the user can see and interact with
  * a set of skills and tools for the player to generate ideas, plan and execute experiments, run tests, interact with softmax, do research, and everything else they need to do
  * some number of separate agents/sub-agents with their own harnesses or at least instruction files that do specific tasks such as the ones above
  * a way for the user to interact directly with multiple instances of the player in two ways: short term interactive sessions and instantiating long-term loops which either perform a repeating task or have a long-horizon goal
  * separate coworld labs which separate coworld-specific knowledge and have unified coworld-agnostic knowledge, as is this case currently, but mirrored in the visual UI
  * tight integration with Softmax via tooling and UI, including easy querying/dowloading episodes/replays/logs/etc. and easy replay integration, likely with coworld-specific aspects

### Collaborative Wiki w/ Mutual Editing
One capability I want is a wiki-style knowledge-base which organizes the player's knowledge and presents it to both the player and the user in ways each of them understand. The player should have this wiki as a library of linked, indexed markdown files which it can build up and modify. As I will mention later, we'll want to build tools and skills to allow the player to use sub-agents to manage this wiki effectively. In addition to the wiki files themselves, we'll need tooling that allows the agent to easily search the wiki, makes the knowledge available at the right time, etc. Probably we can just start out with an index file? The final design of the player side of this system should be based on SOTA agentic memory systems, which we'll need to actually research using web-search tools.

The user side of the wiki should be a section of the webUI; the exact details are fuzzy, but I have a few requirements for it:
  * It must support images, tables, figures, diagrams, charts, etc. This could either be `.md` files with all figures being images, or HTML files rendered from the player-side `.md` files like with the `generate-report` skills you have, or some kind of templating system which renders the player-side `.md` files in something like a Wikipedia format. 
  * The user should be able to edit the wiki pages directly, and when the user edits the files the player should, in some way, be alerted. Right now, I envision this alert looking like a sub-agent getting woken up and given the diff, and asked to incorporate the changes in the broader wiki (i.e., add cross-links, update other pages with the new information, etc.) and into the broader player knowledge, such as by updating experiments in progress. 
  * The user should have access to a change-log and get notifications when the player makes changes, so that, in the same way the player can respond to user edits, the user can see and respond to player edits. 
  * The user should also be able to make text-associated comments on the wiki which the player can then respond to, so that the user can ask questions, point out concerns, etc. in an easy and intuitive interface rather than needing to either open a full agent session or make manual rewrites themself.
  * Wiki history should be tracked, with edits recorded and associated to the user or player.
  * Slightly redundant with one of my above points, but we'll want a cron job sub-agent which regularly maintains the knowledge base, ensuring its up-to-date and well-organized.

The contents of the wiki should include reports and knowledge about coworlds and Softmax in general, the mechanics and details of specific coworlds being played, field reports, opposition research, web research on similar games, and more. A special category of wiki article(s) is the player's strtegy for a game. I'll mention this later, but I'd like the new system to start enforcing or at least enabling having natural-language descriptions of strategies in `.md` files be the "core" of the strategy and the particular implementation in code being based on that core. Thus, changes to the strategy `.md` files must directly result in corresponding changes to the policy code. 

### Ideation and Experimentation Lifecycle
A core part of improving a policy is coming up with ideas for how the policy could be made better, then running experiments to test those ideas and recording your results. This can be a difficult process, but there are a handful of basic stages on the pipeline from ideation to complete experiment. Roughly, I see the following stages:
  * Ideation: Come up with ideas that will improve the policy in some way. These can be vague and are usually generated either from theory-crafting (i.e., just thinking about the game mechanics and thinking about how to use them effectively) or from observation of agent performance.
  * Hypothesis generation: Given an idea, generate a specific, testable intervention which will try out the idea. A hypothesis is one more-or-less-concrete instantiation of an idea; thus, a hypothesis must be a plausible approach to realizing the idea, but a failed hypothesis does not necessarily disqualify the idea. A hypothesis should also specify how it can be falsified and the justification for believing it will really test the idea.
  * Experimentation: Take a hypothesis and then plan and implement its intervention, then test the resulting policy. Just as an idea can lead to multiple hypotheses, a hypothesis can have multiple experiments. Each experiment should lay out a specific implementation design and plan, justifying how that implementation genuinely tests the hypothesis. 
  * Analysis: Once a particular experiment is run, its results must be analyzed and a conclusion drawn. The analysis of an experiment should gather up all the artifacts generated by running the experiment, such as logs, results files, replays, etc., and analyze them to determine the outcome of the experiment. This outcome should then be compared against the hypothesis in two ways: first, do the results *invalidate the experiment* by showing that the experiment really tested something else. Second, if the experiment is valid, do the results *falsify the hypothesis*? 

This pipeline, or something pretty similar to it, exists already in the lab setup. Compare what is established in the lab right to the above and let me know what the differences are. The novelty here will be exposing each stage of the process to the user, allowing the user to deep observability of both past and current experiments in the pipeline. The design questions here are about how this information is exposed to the user. This interface also needs to be collaborative. The user should be able to suggest new problems/topics, ideas, and hypotheses, and should be able to comment on, edit, etc., experiments and conclusions. It's crucial that the player can present its experimental setup, its evidence, and its conclusions to the user and that the user can provide feedback which is incorporated into the improvement loop the player is running. 

I currently envision a few kinds of entities, which are organized hierarchically, such that ideas contain hypotheses, which contain experiments and their results.

#### Topics
A topic is just some thing we want to address, whether that's a behavioral issue in the policy, something the policy is bad at, some strategy we want to try, etc. A topic might have a stated goal or outcome, such as improving shot accuracy or increasing last hits; it might specify an intervention, such as increasing fire rate or using movement to cancel attack backswings; it might have a new strategy component, such as trying a flanking maneuver or rotating to empty lanes for farm; or it might have something else. The core thing is that each topic includes a write-up describing what is being investigated and why. Topics can be generated either by the player or the user.

#### Hypotheses
Hypotheses are specific, testable interventions which address one or more topics. Unlike a topic, which might be quite vague, a hypothesis should be fairly specific. It should list a particular set of inteventions, whether strategic, tactical, or mechanical, and the expected outcome of these changes. It should allow the player to generate and propose experiments which test it, such that the experiment proposals can be evaluated in terms of whether they really test the hypothesis. In the same vein, the hypotheses should be evaluated against the topics they address for whether they really make sense as a solution/attempt/intervention that would properly address the topic.

#### Experiments
An experiment is associated with a particular hypothesis and describes one or more concrete implementation-level changes to the policy, how this change will be evaluated, and a justification for why the change and its evaluation genuinely test the hypothesis, keeping in mind the hypothesis' own claims and the broader topic(s) the hypothesis is attempting to address. Experiments have a full life-cycle of their own, including proposal, implementation, and execution, which should be recorded. Experiments are the purview of the player; the user might suggest experimental setups in topics or hypotheses, but it's up to the player to actually generate, propose, and execute experiments.

#### Results and Analysis
Once an experiment is run, it produces results and the consequent analysis of those results. This should include all the evidence and artifacts from the experiment, such as result files, scores, replays, logs, etc., as well as the player's analysis write-up and conclusions. 

All of these entites should be stored in a way that's easy for both the player and the user to interact with. It seems likely that whatever format we use for the wiki pages will be reused here, though with a different connective structure, especially on the user-facing UI. As with the wiki pages, collaboration is key, and the user should be able to comment on and edit these entities just as much as the player can. 

### Robust Player System
As noted above, the "player" is a complete system, not a particular agent, and that player system will look like should be an upgraded, expanded version of the current setup turned into a complete harness, with elements of paperclip/gastown where there are sub-agents for different tasks. There are probably a lot of components to this, but here are some that I'm thinking about:
  * Scheduled autonomous agents with specific instruction files, skills, and tools which handle regular tasks such as knowledge maintenance, forum/wiki interactions, experiment monitoring, etc. which need consistent effort to maintain and don't require user intervention.
  * Triggered autonomous agents which are triggered when some event happens or when the user requests it and have a fixed job with custom instructions, skills, and tools to handle tha job. For example, when an idea is generated or updated, a hypothesizer agent might be spun up and tasked with generating some new hypotheses for the idea, then an experimenter agent might be spun up for each hypothesis, so the creation of a new idea immediately leads to agents working on that idea. 
  * A combination of the above, such as a librarian agent which is regularly woken up to ensure the wiki is accuracte, up-to-date, and complete but which is also spun-up whenever the user makes changes to go incorporate those changes.
  * Invoked interactive agent sessions which the user can spawn and interact with directly, for general tasks and especially for tasks which benefit from human oversight.
  * Robust inter-agent communication via an internal forum/message board, inter-agent direct messages, and possibly even a social media like board where agents can post what they're working on.
  * Spend and observability tools for the user to have insight into which agents are spending how much and why, what agents are doing, etc.
  * Skills and tools like what we have now, but also possibly expanded and upgraded. Tools and skills for interacting with the Observatory in a variety of ways, for performing the various tasks and for the various agents we'll be using, etc.
  * A meta-agent for creating new agents and modifying the harness itself. 
  * Interop with both Claude Code and Codex

Many of these components are underspecified in my head right now, and can probably be fleshed out well by doing research into what the SOTA looks like, so that'll be a first step on this portion of the project. 

### Agents in the System
Although not complete, I've laid out some examples of the agents I think will be important in the player system below. Some useful terms:
  * *Autonomous vs interactive:* An autonomous agent is one which largely acts on its own with minimal or no human intervention, while an interactive agent is one which is driven by interaction with the user. The driving aspect is the most important here: autonomous agents can ask for help, ping the user occasionally, etc., but they should drive themselves and seek advice only when blocked or in a non-blocking manner. Interactive agents are more like typical Claude Code or Codex sessions, just with instructions and skills tuned to their particular job.
  * *Scheduled:* A scheduled agent is one that is woken up at regular intervals to do its job, just as it says on the tin. A scheduled agent must at least be capable of being autonomous, because it must be able to complete its job at regular intervals without needing the user to get back on the computer even time the agent is woken up. Scheduled agents are good for tasks which require consistent, predictable maintenance
  * *Triggered:* A triggered agent is one that is woken up by some trigger and responds to that trigger based on its instructions and with its skills and tools. Since the triggers might be automatic things (such as new opponent policies being submitted, changes to a coworld, new ideas being created, etc.) triggered agents must be able to operate autonomously for much the same reasons as the scheduled agents. 
  * *Invoked:* An invoked agent is one which the user specifically invokes, and is more likely than other agents to be interactive rather than autonomous. Other than the (kinda degenerate) case where a user manually invokes an agent that is otherwise triggered (i.e., a manual triggering), invoked agents ae generally invoked by the user to some interactive task/session.

Note that most agents will be all of these to some extent; an agent is really just a particular instruction file (`AGENTS.md`/`CLAUDE.md`) and a set of tools and skills and knowledge; whether the agent is running autonomously or interactively, or how it was created, dictate some of its instructions but not most of them. For example, a particular agent that's started autonomously might have the same instructions as one started interactively, except that the autonomous version has additional instructions for operating with minimal human interaction.


Some possible agents:
  * *Librarian:* The Librarian agent mostly runs autonomously on a schedule and is responsible for ensuring all knowledge about the coworld is accurate and up-to-date, and for generally managing the wiki, keeping it clean and well-organized, responding to user changes, etc. 
  * *Scientist:* Responsible for generating hypotheses, running experiments, and analyzing results for ideas in teh experiment pipeline. 
  * *Strategist:* Responsible for generating strategy ideas for policies and for trying to interpret the strategies of other players based on their policies' actions. 
  * *Manager:* An agent which is responsible for managing, improving, and even "hiring" other agents. It needs to set responsibilities, goals, and expectations for the other agents, then evaluate their performance and work with the user to improve them.

This list is probably not complete and these agents may end up being too big and get broken up into smaller roles.
