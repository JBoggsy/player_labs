# Vision and goals

This document states *why* the project exists and *what* its major parts are.
The other design documents detail each part.

## The problem being solved

Today the lab is a set of directories, skills, and markdown files that a coding
agent works through in one terminal session at a time. The human sees the agent's
knowledge, beliefs, and actions only by reading files or watching a session. Long
running work (monitoring an experiment, maintaining knowledge, tracking the field)
has to be babysat, and only one thing happens at a time.

The Player Agentic Development Environment (Player-ADE) upgrades this into a
web-UI-based environment where a human and a system of coding agents develop game
policies together, with many agents working in parallel over long horizons.

## Three aims

1. **Significantly improve the user's experience** of developing and improving
   policies with coding agents.
2. **Upgrade the existing general-purpose, game-agnostic tools, skills, and
   knowledge** in the lab.
3. **Enable parallel, long-running agentic tasks**, providing both the harness that
   runs them and the UI/UX the user needs to interact with them.

## The core idea: collaboration between user and player

The user and the player (the agent system) collaborate. For that to work:

- The player needs the skills, knowledge, and tools for policy development *and*
  for interacting with the user.
- The user needs observability into the player's knowledge, actions, beliefs, and
  strategies, and needs to be able to both direct the player and respond to the
  player's needs, actions, and questions.

The player is meant to be more autonomous than today's lab agent. The user
directs and collaborates; the user is not a gate the work has to pass through.
Which specific gates remain is [Q28](05-open-questions.md).

## Foundation: CAOS

The system is built on **CAOS**, the Content-Addressable Operating System that
Softmax is developing. In CAOS, files and the programs, functions, and tool calls
that act on them are all hashable, so every change and every action is accounted
for. It serves two roles here from the outset:

- the **history system** for the wiki, the pipeline, the policy versions, and
  everything the player does;
- the **harness** the agents run in, starting with the single phase-1 agent.

CAOS is a work in progress and neither the user nor the scribe fully understands
it yet. Understanding it and standing it up is the first task
([07-research-plan.md](07-research-plan.md), area 4).

## Principle: natural-language strategy is the core of a policy

A policy's strategy is written in natural language in markdown files, and the
code is derived from that written strategy. The strategy documents are the true
description of the policy; the code is a "compiled" version of them, where the
compilation is the coding agent writing or editing the code from the strategy.
A change to the policy is written into the strategy documents first and then
compiled. The mechanics are in the [wiki document](01-collaborative-wiki.md).

## Principle: prose is current, history is kept

Any prose that describes or prescribes the current state (a wiki page, a
strategy document, an entity's write-up) describes the present only. History is
kept in full, in structured, dated, versioned records: edit histories, the
pipeline, the policy version tree, and CAOS. See
[01-collaborative-wiki.md](01-collaborative-wiki.md).

## What is not yet designed

The agent system beyond the single phase-1 agent (how agents are scheduled and
triggered, how they talk to each other, how the roster grows) is recorded as
requirements in [03](03-player-system-harness.md) and [04](04-agents.md) and is
designed in a later phase.
