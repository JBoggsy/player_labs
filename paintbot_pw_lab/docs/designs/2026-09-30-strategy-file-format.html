The strategy file and its compilation to BASIC

The Paintbot PW lab writes its policy as one structured Markdown file. A separate LLM agent compiles that file into a plain BASIC script.

Executive Summary

The strategy file is the source of truth for our Paintbot PW policy. The compiled BASIC script is a build product. We change the policy only when we edit STRATEGY.md. Then a separate LLM agent compiles that file into policy.bas, and nobody edits the compiled script by hand. The compiler never edits the strategy file. It writes each guess and each gap into a versioned compile report, and the edit loop decides which guesses go into the strategy file. There is one kind of authored BASIC: skill code. Each Skill has a skill.bas file that we write directly, and the compiler copies it into the build unchanged, because it is source and not output.

The file has six layers, from Primitives at the bottom to Strategy at the top, and two side sections: Adaptations and Communication. Each layer can refer only to layers below it. Each component is precise Simplified Technical English prose with a fixed set of labeled fields, thus a linter can check the file. Every component carries checks at five levels: true, believed, acted, acted properly, and result. Telemetry v2 logs the beliefs and decisions that these checks need, because the replay already holds every position and every executed command.

Status This proposal is dated 2026-09-30. We revised it after James's review. Nothing here is implemented. The strategy/ paths, the telemetry v2 line kinds, and the pw.py strategy lint, pw.py strategy trace, and pw.py strategy audit commands are proposed names. The compile process (versioning, reports, incremental builds) gets its own design document later. This document sets only the constraints that the compile process must obey.

1 · The load-bearing rule

  • The strategy file is the source. The compiled .bas is a build product, and nobody edits it by hand.
  • The compiler never edits the source. Its guesses and gaps go into a versioned compile report.
  • skill.bas files are authored source. The compiler copies them unchanged.
The rule The strategy file is the source of truth for our Paintbot PW policy. The compiled BASIC script is a build product.
  • We design, discuss, and change the policy when we edit the strategy file.
  • A separate compile step (an LLM agent) turns the strategy file into a .bas script.
  • Nobody edits the compiled .bas by hand. To change behavior, change the source and recompile.
  • The compiler never edits the strategy file. It writes every guess and every gap into a separate compile report. The report is versioned and linked to the policy version. The edit loop reads the report and decides if a guess goes into the strategy file.
  • We can trace every compiled script to the exact source that made it (section 8).

There is one kind of authored BASIC: skill code (section 4.1). Each Skill has a skill.bas file that we write and improve directly. We do this because work on mechanics is more productive in code than in prose. skill.bas is source, not output. The compiler copies it into the build unchanged and never makes it again. The rule above still applies to the compiled .bas, with no exception.

The rule must be visible at every level. It appears as a banner at the top of the strategy file and as a "generated, do not edit" header in every compiled .bas. It also appears as a line in the lab AGENTS.md and in the lab WORKING_CONTEXT.md1.

We use plain BASIC. The neural lane and the jev.bas oracle lane are out of scope.

2 · Goals and non-goals

  • One readable specification that a compiler agent can use and a script can lint.
  • Modular: one component maps to one named unit of BASIC.
  • Checks against replays at five levels, and traceability in two directions.

Goals

  • One readable specification. It says what our agent knows, what situations it recognizes, and what it can do. It also says how the agent chooses, how it adapts, and what it tells teammates.
  • Machine-usable. A compiler agent can find every component, resolve every reference, and report what it could not compile. A script can lint the file.
  • Modular. One component maps to one named unit of BASIC. When a component changes, the compiler knows which unit to change, and nothing else changes. We can practice and improve a Skill or a Capability alone. The improvement touches other code only where it must.
  • Checkable against replays at five levels (section 5). Was it true? Did the agent believe it? Did the agent act? Did it act properly? Was the result what we expected?
  • Traceable in two directions. We can go from a component to its BASIC. We can also go from a replay, through telemetry, back to the component, the rule, and the beliefs that were active.

Non-goals

  • A general behavior-tree or planning language. The file describes one policy for one game.
  • Exact executable semantics. Components are precise technical prose, not code. Precision comes from numbers in Spec and Params. It also comes from the compiler, which reports each point that was not clear.

3 · Structure: six layers and two side sections

  • Six layers, bottom to top: Primitives, Knowledge, Situations, Skills, Capabilities, Strategy.
  • A layer can refer only to layers below it.
  • Two side sections, Adaptations and Communication, come after the layers. Each has stated exceptions.
  • Each tick has a fixed order of seven steps, and the compiler must obey it.

The file has six layers, bottom to top, and two side sections after them. A layer can refer only to layers below it. The side sections have the specific exceptions that their rows in the table give. Figure 1 shows the structure.

SectionPrefixWhat it isMay refer toPaintbot PW examples
PrimitivesP.What the engine already does. Listed, not authored.—walkTo, lookAt, shootAt, chargeGrenade, sneak, shout2
KnowledgeK.What the agent knows at runtime: direct reads from the host, plus beliefs and memory built from them.P., and COM. messages as a sourcevisible enemies and their motion; remembered pickups; heart ownership; team lives lead; last-heard gunfire sector
SituationsS.Named states of the world, defined over Knowledge.K.outnumbered near our heart; enemy capturing a heart we own; ahead on lives late in the match
SkillsSK.Motor skills: parameterized chains of primitives that we must execute better than other bots. No goals of their own.P., K., S.move-and-shoot (strafe legs timed to gun windup); lead aim; grenade throw at range; dry routing around water
CapabilitiesC.Tactical sub-objectives, built from Skills, each with success and abort conditions.K., S., SK.push to heart, hold heart, attack heart, retreat to heart, grab supply, snatch glory heart
StrategyST. / R.Roles, the prioritized rules (R.) from Situation to Capability, and commitment.all layers above"two cogs per squad capture, two cover"; "when ahead on lives after 5:00, hunt instead of capture"
AdaptationsA.Rules that change rule priorities during a match.K., S., and R. rules (priorities only)"if our pushes to the far heart fail 3 times, lower R.push_far by 20"
CommunicationCOM.Messages we send and understand: content, encoding, when sent, and which Knowledge a heard message updates. A parallel track to the main decision.everything (the send side reads this tick's decision)"announce my target heart"; "report enemy count at my heart"

Why Skills and Capabilities are separate. Skills hold mechanical quality (aim, footwork, timing), and many Capabilities use the same Skill. Capabilities hold tactical intent. Thus we can improve "move and shoot" once, and every capability that fights gets the benefit. We can also A/B a tactic and not touch the mechanics.

Why Situations are separate from Strategy. Several rules can use the same situation. A situation is also a claim about the world that we can check against replays. A rule is a choice that we can A/B.

Why Adaptations and Communication are side sections, not layers. An Adaptation must name the rules that it changes, thus it comes after Strategy. Communication operates on both ends of the tick. Heard messages become Knowledge before the decision, and sent messages report the decision after it. When both stay outside the stack, the downward-only rule of the stack stays simple. The linter checks the two stated exceptions.

Per-tick order (the compiler must obey it)

The engine starts the script from the top every tick, and only globals and arrays persist3. In each tick, the compiled script does these steps in this order:

  1. Decode heard messages (COM. receive side) and update Knowledge (K.).
  2. Evaluate every Situation (S.) once, into flags.
  3. Apply Adaptations (A.) to rule priorities.
  4. Select the rule (R.): the highest current priority whose condition holds, subject to ST.commitment.
  5. Run the selected Capability (C.). It calls Skills (SK.), and the Skills call primitives.
  6. Send messages (COM. send side).
  7. Write telemetry (section 6).

4 · Format: structured Markdown in Simplified Technical English

  • One Markdown file with a fixed heading scheme, stable IDs, and a fixed set of labeled fields for each component.
  • Rules have numeric priorities. The highest current priority whose condition holds wins.
  • Learned constants go in Params, not in Knowledge.
  • All prose is ASD-STE100 Simplified Technical English, because the reader is a compiler agent.

The format is one Markdown file with a fixed heading scheme, stable IDs, and a fixed set of labeled fields for each component. It is not JSON, YAML, or XML. Section 11 gives the comparison.

4.1 File layout

paintbot_pw_lab/strategy/
  STRATEGY.md                  # the source of truth (this format)
  skills/<skill_name>/
    skill.md                   # optional: the full Skill spec, linked from STRATEGY.md
    skill.bas                  # authored skill code (source, not output)
  compiled/<build>/
    policy.bas                 # compiler output; generated, never hand-edited
    map.json                   # component ID -> BASIC unit, telemetry codes, @tune constants
    report.md                  # guesses, gaps, questions, budget measurements
    version.json               # section 8

There is one STRATEGY.md for now. Any section can link to a separate file for that section when it becomes large. Every Skill has a directory from the start, because every Skill has its own code.

  • Every component is a level-3 heading, and the heading text is its ID: a prefix plus a snake_case name.
  • Rules inside ST.rules have their own IDs (R.<name>). Thus logs, checks, and Adaptations can name them.
  • IDs are stable. A new name for an ID is a deliberate change, and the linter reports it.
  • A reference is the bare ID in backticks (`S.outnumbered`). The linter resolves it.

4.3 Fields

Each component is a heading, then a bullet list of labeled fields, then optional prose. A field with * is necessary.

FieldUsed byMeaning
Summary*allOne sentence.
Spec*allWhat the compiler must implement. Precise: distances, ticks, order.
SourcesKHost reads it uses (playerX, controlOwner, heardX ...) and COM. messages that update it.
MemoryKWhat persists across ticks and for how long.
LogKThe belief values telemetry records, and how often (section 6). Required if the component has a Believed check.
UsesS, SK, C, R, A, COMIDs of components it depends on.
ParamsS, SK, C, R, ANamed numbers: value, units, range [min, max, step] if tunable, and why this value (hand-set, or tuned, with a link to the tune run).
CodeSKPath to skill.bas.
Done when / Abort whenCSuccess condition; conditions that give control back to Strategy. Each has a stable name, so telemetry can say which one fired.
Checks*all but PThe five-level checks (section 5).
EvidenceallLinks: TENTATIVE_LESSONS4, reports, A/B results, tune runs.

RationaleallWhy. For people and the edit loop. The compiler does not implement rationale.

Learned constants go in Params of the component that uses them (for example, "lead a moving target by lead_ticks = 6"). They do not go in Knowledge. Knowledge is what the agent learns about the world while it plays. When the tuning loop finds a better value, the edit loop writes the new value into Params with an Evidence link to the tune run. If the edit loop does not do this, the next recompile loses the value.

4.4 Strategy: rules with priorities

ST.rules is a list of rules. Each rule has an ID and a default priority (0-1000). In each tick, the rule with the highest current priority whose condition holds wins. File order breaks ties.

### ST.rules
- `R.dump_grenade` [900]: WHEN `S.about_to_die_with_charge` DO `C.dump_grenade`
- `R.retreat` [700]: WHEN `S.outnumbered` AND NOT `S.on_owned_heart` DO `C.retreat_to_heart`(toward=nearest_friend)
- `R.defend` [600]: WHEN `S.enemy_capturing_our_heart` DO `C.attack_heart`(heart=that_heart) FOR role=cover
- `R.hunt` [400]: WHEN `S.ahead_on_lives` AND `S.late_match` DO `C.hunt`
- `R.push` [100]: ALWAYS DO `C.push_to_heart`(heart=squad_target)

ST.roles says how the eight cogs on a team divide into roles. All eight cogs operate the same file. Thus roles are a function of selfId, as the squads in base.bas are5.

ST.commitment says when a new rule can interrupt a capability that is active. It gives minimum hold times, the priority margin that a new rule needs to preempt, and hysteresis. As a result, the agent does not change capability every tick.

4.5 Adaptations

An Adaptation changes rule priorities during a match. This is the first form of a policy that changes its own structure. We keep it small on purpose.

### A.demote_failed_push
- Summary: Stop pushing a heart that keeps failing.
- Spec: When `K.push_history` shows `fail_limit` failed pushes to one heart within
  `window` ticks, lower `R.push` priority for that heart by `step`. Restore it after `window`.
- Uses: `K.push_history`, `R.push`
- Params: fail_limit = 3; window = 1440 ticks [480, 2880, 240]; step = 50 [10, 100, 10]

There are two limits. First, globals reset every episode, thus an Adaptation lasts only for one match. Second, telemetry must log every priority change (section 6). If it does not, we cannot compute the "acted properly" check.

4.6 Communication

A Communication component defines one message type. It has these fields:

  • Content: the beliefs or intentions that the message carries (for example, my target heart, or the enemies that I see).
  • Encoding: the exact text or numeric format. Keep it short, because shout costs 68 work units.
  • Send when: the condition. It can refer to the rule and capability that this tick selected.
  • On receipt: the K. component that the message updates, and how much to trust it.
  • Checks: Was the message sent when it must be? Did teammates decode it correctly? Did it change the result?
Engine constraints Every living cog within 12.8 m hears a shout, and this includes enemies. A cog can send at most 4 shouts per tick. Delivery occurs on the next tick. A heard message gives the observed seat and the exact position of the speaker2. Communication needs more design (section 12).

4.7 A worked component

The example below shows a full Capability with all of its fields.

### C.hold_heart
- Summary: Keep a heart that we own from capture.
- Spec: Stand inside the capture ring of `heart`. Stay off the line between the ring center
  and the nearest remembered enemy. Face the most recent threat direction. Fight with
  `SK.move_and_shoot`. Do not go more than `leash` outside the ring.
- Uses: `K.enemy_contacts`, `K.threat_direction`, `SK.move_and_shoot`, `SK.lead_aim`
- Params: heart (heart index); leash = 300 cm [100, 800, 50], hand-set, no tune run yet
- Done when: never (runs until Strategy selects a different rule)
- Abort when: `outnumbered_hold` = `S.outnumbered` true for 24 ticks; `heart_lost` = the heart
  is not ours
- Checks:
  - Acted properly: while active, the cog is within ring + `leash` in >= 95% of ticks. (script:
    `pw.py strategy audit --check C.hold_heart.leash`)
  - Result: the heart stays ours for the whole activation in >= 60% of activations. (replay stat)
- Status: idea (2026-09-30)
- Rationale: base.bas has no hold behavior. It moves on when a heart is ours ...

4.8 Prose style

All prose in STRATEGY.md and skill.md is ASD-STE100 Simplified Technical English. It has short sentences, one meaning per word, active voice, and no hedges. The text is a technical specification for a compiler agent, not a guide for people. Precision and no ambiguity come first. Rationale uses the same style. The linter flags the mechanical violations: semicolons, "may/should/would", and sentences over 25 words.

5 · Checks: five levels

  • Five levels, each on top of the one before it: True, Believed, Acted, Acted properly, Result.
  • Each check has a semantic description, a script, or a replay statistic. At least one is necessary.
  • A check that the logs cannot compute reports unmeasurable. It never passes by default.

Every component carries checks that we can compute from replays and telemetry. There are five levels, and each level builds on the level before it.

LevelQuestionData needed
TrueWas the thing actually true or applicable?The replay (ground truth).
BelievedDid the agent believe it was true?Telemetry: logged beliefs and situation flags.
ActedIf it believed it, did it act on the belief?Telemetry: the rule and capability selected.
Acted properlyIf it acted, did it act as the strategy says?Telemetry: the decision inputs (flags, priorities, commitment state), capability events; replay for the executed commands.
ResultIf it acted properly and the belief was correct, was the result what we expected?Replay outcomes over the capability's activation window.

The next table shows the levels that apply to each section.

SectionChecks that apply
KnowledgeTrue vs Believed = belief accuracy (for example, logged enemy positions against replay positions; error in cm, false and missed contacts).
SituationsTrue, Believed, and their agreement (precision and recall of the flag).
RulesActed (the rule fired when its condition held and it was the top priority), Acted properly (the audit re-runs the selection from logged inputs and gets the same rule).
CapabilitiesActed properly (Spec, Done/Abort), Result.
SkillsActed properly (execution: for example, shots fired only after windup), Result (for example, hit rate at range).
AdaptationsActed (fired when its condition held), Result (did the new priorities help).
CommunicationSent correctly, decoded correctly by teammates, Result.

Each check has one or more of these: a semantic description, a script to run, and a replay statistic. At least one is necessary. A check that the logs cannot compute reports unmeasurable. It never passes by default.

Belief building (Knowledge) is imperfect by nature, because the data has fog. Belief-accuracy checks let us optimize belief building from replays, as we do for any other component.

6 · Telemetry v2

  • Telemetry v2 logs only what is in the head of the agent: beliefs and decisions.
  • Five proposed line kinds, with integer fields only. map.json decodes every code.
  • The print budget per tick is a hard limit. If a tick goes above it, the seat is disabled for the episode.
  • Hosted episodes return our seat logs. No hosted episode has carried our telemetry lines yet.

Telemetry v1 prints one PWI line with a mode code, a target, and a reason6. pw.py intent parses that line7. v2 must give every value that a Believed, Acted, or Acted properly check needs. The replay already contains every position and every executed command. Thus telemetry logs only what is in the head of the agent: beliefs and decisions.

The line kinds below are proposed names. All fields are integers, and map.json decodes every code to its ID.

LineWhenFieldsServes
PWD decisionon any change, and every 24 tickstick; rule code; capability code; capability params (up to 3); situation flag words (31 flags per word); held (1 = kept by commitment, 0 = new selection); priority-set versionSituations Believed; Rules Acted and Acted properly; Capabilities Acted
PWP prioritiesat start, and when an Adaptation changes onetick; adaptation code; rule code; old priority; new priority; priority-set versionre-running the selection; Adaptations Acted
PWE capability eventon start, done, aborttick; capability code; event; condition code (which Done/Abort condition)Capabilities Acted properly and Result (activation windows)
PWB beliefper the K. component's Log fieldtick; knowledge code; the logged values (for example seat, x, y, age for each believed enemy)Knowledge belief accuracy; Situations Believed

Rules for telemetry v2

  • Alignment. tick is worldTick at decision time. It equals the replay table tick of the world that the agent used for the decision. The command appears at tick + 1, as in v17.
  • Coverage is checked, not assumed. For each check, map.json lists the log fields that the check reads. The linter fails a check when no component logs its fields.
  • Budget. In each tick, the engine permits 1,024 printed bytes and 128 print events. If a tick goes above either limit, a runtime error disables the seat for the rest of the episode3. The compiler reports the worst-case total per tick and keeps it at or below half of each limit6. Large belief lists are split across ticks (for example, 4 enemies per tick). The engine cuts the seat log at 10 MiB per episode3. The target is at most 2 MiB for a 14,400-tick match.
  • Kill switch. telemetryOff = 1 stops all lines.
  • Tooling. pw_intent.py gets a v2 parser and the five-level audit (section 10).
Hosted logs: available, with two caveats Our XP episodes return one seat log for each of our seats (logs/policy_agent_<seat>.log). The seed pilot of 2026-09-30 confirmed this, and the engine writes PRINT output into that file8. Caveat 1: no hosted policy of ours printed anything yet, because base.bas prints nothing. Thus the first telemetry v2 upload must confirm that the lines arrive complete. Caveat 2: some logs are missing for minutes after an episode ends (5 of 32 of our seat logs in the first fetch of the pilot). Refetch with --force. The audit reports a seat with no log as unmeasurable. Logs come back only for our own seats, thus belief checks apply only to our own seats.

7 · The two loops

  • The edit loop (people and an LLM) changes the source. It never edits compiled output.
  • The compile loop (a separate LLM agent) makes one build directory. It never edits the source.
  • Compiler guesses go back to the edit loop, and the edit loop decides.
  • Nothing uploads without a clean local compile and a local screen.

Different actors operate the two loops, and the source is where the loops meet. Figure 3 shows how they connect.

The edit loop

People and an LLM operate the edit loop on STRATEGY.md and skills/. The edit loop does these tasks:

  • Read the evidence: field reports, replays, check results, A/B results, and compile reports.
  • Change components.
  • Practice skills: improve skill.bas against the checks of the skill.
  • Keep Status, the Params values, and Evidence current.

The edit loop never edits compiled output.

The compile loop and its contract

A separate LLM agent operates the compile loop. Its input is STRATEGY.md, the skill.bas files, the policy surface of the lab, and the reference/ starters as a library of proven BASIC. Its output is one compiled/<build>/ directory. Its contract has nine items:

  1. Never edit the source. Do not write to STRATEGY.md or skills/.
  2. Compile only committed source. If STRATEGY.md or skills/ has uncommitted changes, refuse to build. Thus the commit SHA in version.json identifies the input exactly.
  3. Structure and modularity. Obey the per-tick order (section 3). Write one SUB (or one delimited block) for each component. Name it from its ID, and put the ID in a comment. The globals of each component share a prefix that comes from its ID. map.json records every unit. Thus a later build can change only the units whose components changed.
  4. Skills verbatim. Copy each skill.bas unchanged. If the code of a skill does not fit (a missing global, a budget problem), report it. Do not rewrite it.
  5. Parameters become constants in one init block. Each tunable constant carries ' @tune min max step9. Thus the paintbot-pw-tune skill can search them without a recompile10.
  6. Telemetry v2 as section 6 specifies, with the budget report.
  7. Report every guess. Where Spec is ambiguous or impossible, choose the most conservative reading and implement it. Record it in report.md with the component ID. An unresolved guess blocks Status: tested.
  8. Safety and budget. The build must compile locally (pw.py local compile)11. The report gives peak instructions and work units against the per-tick budgets of 50,000 and 125,0003. A compile error fails the whole hosted episode12. Thus nothing uploads without a clean local compile and a local screen11.
  9. Header. policy.bas starts with a banner: the build ID from version.json, and "generated, do not edit".

Compile incrementally. A full recompile for every change makes large diffs with much noise. The compiler takes the policy.bas and map.json of the previous build and changes only the units whose components changed. A full recompile stays available.

8 · Versioning (outline)

  • A build must identify exactly what it came from.
  • The compiler uses only a committed source.
  • The compile design document gives the details later.

A build must identify exactly what it came from. The compiler uses only a committed STRATEGY.md and skills/ (contract item 2), because an uncommitted edit has no commit SHA. Each build writes version.json with these values:

  • The source commit SHA.
  • The sha256 of STRATEGY.md and of each skill.bas.
  • The sha256 of policy.bas.
  • The date of the compiler run.
  • After upload, the policy ref (name:vN).

The compile report sits next to version.json. Thus a policy version, its source, and its compiler guesses always stay together.

9 · What this does not solve

  • Natural language is ambiguous. We accept this and decrease it.
  • Beliefs can be wrong. Belief-accuracy checks measure this.
  • Hosted telemetry is not yet seen end to end.
Risk: natural language is ambiguous The same Spec can compile to different BASIC in two runs. We accept this. The mitigations are STE prose, numbers in Spec and Params, the incremental compile, and the compile report.
Risk: beliefs can be wrong Knowledge comes from data with fog. Belief-accuracy checks measure this, and we optimize beliefs like any other component.
Risk: hosted telemetry is not yet seen end to end Retrieval of hosted seat logs works, but no hosted episode has carried our telemetry lines yet (section 6).

10 · Tooling (proposed, small)

  • Three proposed commands: pw.py strategy lint, pw.py strategy trace, and pw.py strategy audit.
  • The lint exits nonzero on errors, thus a loop can gate on it.
  • No new dependency.
  • pw.py strategy lint STRATEGY.md --json checks that IDs are unique and well formed. It checks that references resolve and obey the section rules (section 3). It checks that the necessary fields are present. It checks that each Situation, Capability, and rule has a user, and that a component logs the data of each check. It also checks that Params ranges are well formed, and it finds mechanical STE violations. It exits nonzero on errors, thus a loop can gate on it.
  • pw.py strategy trace <build> compares version.json with the current source. It lists the components that changed since that build.
  • pw.py strategy audit <episodes> --json parses telemetry v2 and joins it to the hash-checked replay. Then it computes every check at all five levels. It extends pw_intent.py7.

No new dependency is necessary.

11 · Alternatives considered

  • Structured Markdown wins, because the content is precise prose.
  • Numeric priorities replace ordered rules where the first match wins.
  • Authored skill.bas replaces skills as prose only.
OptionForAgainst
Structured Markdown (chosen)The content is precise prose, which LLM editors write well. Readable and diffable. Headings give structure a linter can parse.Structure is by convention, so it needs a linter.
JSON / YAMLExact structure, trivial to parse.Long prose inside strings is hard to write and review; escaping and indentation errors; LLM edits churn whole blocks.
XMLLLMs handle tags well; exact structure.Noisy for people to read; no gain over Markdown headings at this depth.
Ordered rules, first match winsSimplest to read and check.Priorities cannot change during a match. Replaced by numeric priorities (section 4.4).
Skills as prose only, compiled like everything elseOne rule, no authored BASIC.Mechanics improve faster in code than in prose, and a recompile would discard tuned skill code. Replaced by authored skill.bas.

The design borrows concepts from prior art. Situations plus prioritized rules are utility-based selection: a behavior-tree priority selector with numeric scores. Commitment is BDI-style intention. BDI means belief-desire-intention: an agent keeps a chosen plan until it has a reason to drop it. Skills and Capabilities form a hierarchical state machine.

We borrow the concepts, not a runtime or a file format. There is no behavior-tree runtime in BASIC, and the consumer is an LLM compiler.

12 · Decisions and open questions

  • Three decisions on 2026-09-30: one file, the evidence log, and base.bas as the starting point.
  • Three open questions: communication design, the first hosted telemetry run, and the design of the compile process.

Decided (2026-09-30)

Decision 1 · One file

There is one STRATEGY.md, with optional links to separate files for each section. Skills are directories.

Decision 2 · Evidence log

TENTATIVE_LESSONS.md stays the evidence log4. STRATEGY.md links to it through Evidence. A lesson becomes policy only when it goes into a component.

Decision 3 · Starting point
