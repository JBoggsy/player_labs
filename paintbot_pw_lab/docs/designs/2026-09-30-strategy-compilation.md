## For agents: read this first

- **What this defines:** how a committed source becomes a verified build: the driver, the one LLM
  step, the build layout, `version.json`, the compile report, the five gates, and the compiler
  agent setup for Claude Code and Codex.
- **Read it when:** you implement any `pw.py strategy` subcommand, the runtime library, the
  compiler instructions (`AGENT.md`), or a wrapper; or you run a build and need to read its
  report or gate results.
- **Words:** MUST and MUST NOT are requirements. "Can" is a permission.
- **The invariants:**
  1. The driver MUST refuse uncommitted source (§6).
  2. Only step 2 (Generate) uses an LLM. Rules, priorities, Adaptations, commitment, constants,
     telemetry tables, and the header MUST be generated by Python. The runtime library MUST be
     copied unchanged (§4.1).
  3. The agent MUST write only its unit files and the report draft, in an isolated scratch
     repository; the driver MUST reject the build on any other change and MUST NOT revert
     anything in the user's checkout (§9).
  4. Each LLM component and authored Skill MUST have its own unit file; unchanged units
     MUST be copied, not regenerated (§5, §10). Deterministic `ST.*` components share
     `generated.tables` (§4.1).
  5. A build directory MUST NOT change after it is written: every step, including repair
     rounds, works in a staging directory, which is published once. Uploads go to
     `compiled/uploads.jsonl` (§6).
  6. Every guess MUST be recorded in the report with a stable ID (§7).
  7. A bad seat always fails a build. The local screen MUST NOT veto an intended behavior change
     (§8.2).
- **Start here to implement:** §4 (pipeline), §5 (layout), §8 (gates), §11 (milestones, M0
  first).

## 1. Problem

`STRATEGY.md` is the source of truth for our policy, written in precise natural language. The
league runs one plain BASIC file per seat. We need a process that turns the first into the second
and that:

- produces BASIC that compiles, stays inside the per-tick budgets, and logs telemetry v2;
- changes only the BASIC for components whose text changed;
- records every guess it makes, so the edit loop can resolve it in the source;
- makes every build traceable to its exact source, compiler, and verification results;
- runs inside a session or unattended in an autonomous loop.

## 2. Goals and non-goals

Goals:

- **Reliable where it can be exact.** Anything that can be computed deterministically is done by
  Python, not by the LLM.
- **Modular output.** One component, one BASIC unit file. A change to one component changes one
  unit.
- **Reproducible record.** A build names its source commit, compiler model, compiler
  instructions, and lessons file.
- **Fast.** A small incremental build, verified, in minutes.

Non-goals:

- Byte-identical recompiles. Two LLM runs can produce different BASIC from the same text; we
  accept this (strategy-file-format §9).
- Upload, league submission, and hosted evaluation. The process ends at the local gate. The
  existing skills (`paintbot-pw-ab`, the upload skill) take a build ID from there.
- A custom agent harness. v1 calls an existing coding agent headless (Claude Code or Codex)
  from a small Python driver.

## 3. Prior art

"Spec-driven development" is an established category. The variant in which the specification is
the only artifact people edit and code is generated from it is called **spec-as-source**; that is
our model. The best-known toolkit is GitHub Spec Kit (Markdown specs, validation, generation
through any LLM).

We borrow three ideas: validate the spec before generating, keep one written contract that the
generator obeys, and give every spec item an ID that code and tests trace to. We do not adopt a
toolkit: they are built for one-shot, feature-by-feature application code, and do not handle
incremental regeneration of a single BASIC file under hard per-tick budgets with a fixed runtime
skeleton. Our pipeline is small and specific enough that a few hundred lines of Python plus one
instruction file cost less than adapting a framework.

## 4. Architecture: deterministic steps around one LLM step

| Step | Done by | What it does |
| --- | --- | --- |
| 1. Prepare | Python: `pw.py strategy prepare` | Refuse uncommitted source. Lint `STRATEGY.md`. Hash the source. Compare component texts with the previous build's `map.json` and list components as **new**, **changed**, **unchanged**, or **removed**. Write a work order for the agent. |
| 2. Generate | **LLM compiler agent** | Write one unit file per new or changed component (Knowledge, Situations, Capabilities, Communication). Record guesses. |
| 3. Assemble | Python: `pw.py strategy assemble` | Copy unchanged units from the previous build. Copy each `skill.bas` and each runtime library unit unchanged. Generate the rule table, the constants block, the telemetry code tables, and the header. Join everything into `policy.bas` in the fixed per-tick order. Write `map.json` and `version.json`. |
| 4. Verify | Python: `pw.py strategy verify` | Run the gates (§8). On a failure the agent gets the error and repairs its units; at most 3 rounds. |
| 5. Report | Python + agent | Write `report.json` and `report.md` (§7). |

A Python driver, `pw.py strategy compile`, runs all five steps and calls the agent for step 2
(§9). The driver, not the agent, owns the process, so any supported agent can fill step 2.

**Only step 2 uses an LLM.** Its input is small: the work order, the changed components' text,
their previous unit files, the interfaces of the units they use, `docs/policy-surface.md`, and
`compiler/LESSONS.md`.

### 4.1 What is not LLM-written, and why

| Generated by Python | Reason |
| --- | --- |
| **Rule table** from `ST.rules` (conditions, priorities, capability calls, roles) | The rule syntax is structured (`R.id [priority]: WHEN ... DO ...`). Deterministic code is exact, testable, and needed for the "acted properly" audit, which re-runs selection from logged inputs. |
| **Adaptations table** from `A.` components | Same reason, where an Adaptation is a pure priority change. An Adaptation whose condition needs new logic gets an LLM-written condition unit; the priority change stays generated. |
| **Commitment** from `ST.commitment` parameters | `min_hold`, `preempt_margin`, and `interrupt_at` become constants; the selection algorithm itself (strategy-file-format §4.4) is in the runtime library, mirrored by `strategy_basic.reference_select`. |
| **Constants block** from all `Params` | One init block. Tunable parameters get `' @tune min max step`. |
| **Telemetry code tables** (generated) | Codes for every ID, written to `map.json` and emitted as constants. |
| **Runtime library** (hand-written, in `compiler/runtime/`, copied unchanged): the per-tick skeleton, the telemetry v2 print routines, and (in M3) the comms codec for `strategy/comms.md`'s wire format | This code is fixed: the per-tick order (strategy-file-format §3), a print budget that must be checked once, and exact arithmetic (packing, check, scrambling). It is written and reviewed like `skill.bas`. Which message to send and what a received message does are LLM-written `COM.` units. |
| **Header** (generated) | Build ID, source commit, "generated, do not edit". |

All generated code is one unit, `generated.tables` (`strategy_basic.generate_tables`): the
constants, role, rule and Adaptation tables, and the `st__*` phase dispatch that
`runtime/main.bas` calls. `map.json` maps every `ST.*` component to it (`"generated": true`).

### 4.2 Unit ABI and names

Every name a unit defines starts with its prefix: the ID lower-cased with the dot replaced by
`_`, then `__` (`K.enemy_contacts` → `k_enemy_contacts__count`). IDs never contain `__`, so two
units cannot produce the same name; the runtime uses `rt__` and generated code `st__`.

| Kind | Required SUBs (no arguments) | Contract |
| --- | --- | --- |
| K | `__update()` | every tick, step 1; refreshes its declared outputs |
| S | `__eval()` | every tick, step 2; MUST assign `__on` (0/1) and its outputs on every call |
| C | `__start()`, `__tick()` | `start` once per activation (inputs `__in_*` already bound); `tick` every active tick MUST set `__status` (0 running, 1 done, 2 abort) and, when not 0, `__cond` = a `__k_<name>` constant |
| A | `__eval()` | MUST assign `__fire` (0/1); the effect is generated |
| COM | `__recv()` and/or `__send()` per `Directions` | `recv` sets `__got` and `__from`; `send` sets `__sent` |
| SK | none | `skill.bas`, copied verbatim; its SUBs are callable by components that use the skill |

Every kind can define `__init()`, called once on the first tick. A unit writes only its own
names (never its params, inputs, or condition constants, which generated code sets), reads its
own names, host data, the declared outputs and params of components in its `Uses`, and the
runtime exports `rt__rule`, `rt__cap`, `rt__since`, `rt__pver`, and calls only its own SUBs,
SUBs of skills in its `Uses`, and host functions. A unit has no top-level statements and never
`PRINT`s. `strategy_basic.check_unit` enforces all of this; its diagnostics are the repair-loop
feedback.

## 5. Build layout

```text
paintbot_pw_lab/strategy/
  STRATEGY.md, skills/, comms.md            # source (edited by the edit loop)
  compiler/
    AGENT.md                                # compiler instructions, agent-neutral
    config.json                             # default agent and model
    LESSONS.md                              # compiler memory, reviewed like code
    runtime/lib.bas, runtime/main.bas       # hand-written library: selection, adaptation, telemetry v2; per-tick order
  compiled/
    <build-id>/
      units/<ID>.bas                        # one per LLM component, SK.<name>.bas verbatim,
                                            # runtime.lib.bas, runtime.main.bas, generated.tables.bas
      policy.bas                            # assembled upload file
      map.json                              # ID -> unit, code, globals prefix, text hash, log fields
      version.json                          # §6
      report.json, report.md                # §7
      verify/                               # gate outputs: compile.json, peaks.json, screen summary
    uploads.jsonl                           # append-only: build-id -> uploaded policy ref, date
```

- **Build ID:** `<source short SHA>-<n>`, for example `a1b2c3d-2`; `n` counts builds of the same
  source commit, including failed builds.
- **Staging.** A build is prepared, generated, repaired, assembled, and verified in
  `paintbot_pw_lab/tmp/strategy/<build-id>/` (gitignored), then published to
  `compiled/<build-id>/` once, after the report. Failed builds are published too, marked
  failed: they are never the previous build for an incremental step and are never uploaded.
- **Builds are committed to git.** They are small text, their diffs are worth reviewing, and the
  uploaded artifact stays recoverable.
- **Unit files are self-describing.** Each starts with a comment: component ID, source text
  hash, and "generated, do not edit". Each unit's globals share a prefix derived from its ID
  (`map.json` records it), so units cannot collide.
- **`compiler/runtime/` is authored source,** like `skill.bas`: hand-written, reviewed, copied
  unchanged.

## 6. Versioning

- The compiler builds only from a **committed** `STRATEGY.md`, `skills/`, and `comms.md`
  (compile contract item 2).
- `version.json`:

| Field | Meaning |
| --- | --- |
| `build_id` | as above |
| `source_commit` | git SHA of the source |
| `source_hashes` | sha256 of `STRATEGY.md`, `comms.md`, every `skill.bas`, every runtime unit |
| `previous_build` | build ID used for the incremental step, or null for a full build |
| `compiler` | agent (`claude` or `codex`) and its CLI version, model ID, sha256 of `AGENT.md`, sha256 of `LESSONS.md` |
| `engine` | the `coworld` tag and commit the gates ran against (`tools/release.env`) |
| `policy_sha256` | sha256 of `policy.bas` |
| `gates` | pass/fail per gate (§8) |
| `created` | date and time |

- **Uploads** append to `compiled/uploads.jsonl` (`build_id`, policy ref `name:vN`, date; audits additionally require the
  immutable `policy_version_id` and `policy_sha256`), so a
  build directory never changes after it is written. The link from a league policy version back
  to its source is: policy ref → build ID → `version.json` → source commit.

## 7. The compile report

Two files per build: `report.json` for loops, `report.md` for people. Contents:

- **Units:** each component, with status `new`, `changed`, `reused`, or `removed`.
- **Guesses.** One entry per place where `Spec` was ambiguous or impossible:

| Field | Meaning |
| --- | --- |
| `id` | stable guess ID, `G-<component>-<n>` |
| `component` | the component ID |
| `spec_quote` | the exact text the guess reads |
| `decision` | what the compiler implemented |
| `why` | the reason for that choice |
| `severity` | `low` (a detail), `medium` (changes behavior in some situations), `high` (the spec is contradictory or not possible) |
| `state` | `open`, `possibly resolved` (the component's text changed since the guess), or `closed` (the edit loop confirmed it) |

- **Gaps:** things the spec needs that the engine does not offer, with the substitute used.
- **Gates:** the result of every gate, with numbers.
- **Budget:** peak instructions, work units, and print use per tick.

Guesses carry forward between builds. The edit loop closes a guess by changing the component (or
by recording in `STRATEGY.md` that the guess is the intended behavior); the next build then shows
it as `possibly resolved`, and the edit loop confirms. Any open guess of severity `high` blocks
`Status: tested` for its component.

## 8. Verification gates

All gates run locally against the pinned engine (`tools/release.env`).

| Gate | Tool | Passes when |
| --- | --- | --- |
| G1 Lint | `pw.py strategy lint` | No errors (strategy-file-format §10). |
| G2 Compile | `pw.py local compile policy.bas` | All 16 seats compile and run 720 ticks without being disabled. |
| G3 Budget | a `paintbot-headless` match with `PW_BASIC_PEAKS=1` (per-seat peaks) | Peak instructions and work units at most 80% of 50,000 and 125,000 per tick; worst-case telemetry print at most 50% of 1,024 bytes and 128 events. |
| G4 Screen | `pw.py local screen` (§8.1) | No bad seats in any match. The outcome rule depends on the build's intent (§8.2). |
| G5 Telemetry | record local episodes with seat logs (`pw_intent.py record`; the native library behind `pw.py local` discards PRINT output, although the VM still enforces the print limits) and parse them with the v2 parser | Every line kind this build emits parses, codes decode through `map.json`, and every declared `Log` field and check `Reads:` field appears. |

On G2, G3, or G5 failure the agent gets the error and repairs; after 3 failed rounds the build
stops with a `failed` report. G4 never triggers repair, because "worse" is a strategy question.
A bad seat (a crash or a disabled seat) in G4 always fails the build.

### 8.1 What the local screen is

`pw.py local screen A.bas B.bas --seeds 1-28` plays A against B in the game's native engine on
this machine, under the league's rules and glory settings. Every seed is played twice, A on the
even seats and then on the odd seats, which cancels the side advantage: 56 matches in about 20 seconds with the lab's terrain cache
(3.9 matches/s measured 2026-09-30, plus about 6 s of fixed start-up;
[pw_local.md](../tools/pw_local.md)). It reports:

- `seed_balanced.mean_outcome`: A's mean Elo outcome score (`clamp(0.5 + (A glory - B glory) /
  2000, 0, 1)`), averaged per seed over both sides, with a 95% confidence interval. A policy
  against itself scores exactly 0.5.
- `bad_seats`: any seat that failed to compile or was disabled mid-match.
- `identical_play`: true when the two files played move for move identically.
- Per-seat stats: damage, hits, kills, deaths, captures, first friendly fire.

It is **screening only**. The only opponents are the files we seat, the LLM oracle is off, and
the seeds are not the league's. It answers "is this build broken or clearly worse?", never "is it
better in the field?". The hosted A/B skill (`paintbot-pw-ab`) answers the second question.

### 8.2 The local screen never vetoes a strategy change

The previous build is a weak judge of a behavior change. It can exploit something that works only
against itself, and play is not transitive: a build that loses to the previous build locally can
still do better against the league field, and the reverse. **A behavior change is decided by a
hosted A/B, never by the local screen.** So G4's outcome rule depends on the build's intent, which
`prepare` determines from the source diff:

| Build intent | How `prepare` knows | Reference | G4 outcome rule |
| --- | --- | --- | --- |
| **Behavior change** | a compiler-read field (`Spec`, `Params`, `Uses`, `Done when`, `Abort when`, `Log`), a rule, an Adaptation, `comms.md`, or a `skill.bas` changed | the previous build's `policy.bas` | **Advisory.** The score is reported with its interval. It never fails the build. |
| **No behavior change** | nothing compiler-read changed: a `--full` recompile, a runtime-library, `LESSONS.md`, agent, or engine-pin change | the previous build's `policy.bas` | **Blocking.** `ci95_high >= 0.5`; a clear regression here means the compiler or runtime broke something. |
| **Milestone M1** (the `base.bas` description, §11) | declared by the driver option `--milestone m1` | `reference/base.bas` | **Blocking.** The 95% interval contains 0.5; `identical_play` true is the ideal but not required. |

In every case, a bad seat fails the build. A behavior-change build that scores clearly below its
previous build gets a prominent note in the report, so the edit loop sees it before the hosted
A/B, but it is not blocked.

## 9. The compiler agent

The compiler works with both **Claude Code** and **Codex**. Everything that matters lives in plain
files and a Python driver; each agent needs only a thin wrapper.

- **Instructions:** one plain Markdown file, `strategy/compiler/AGENT.md`: the compile contract
  (strategy-file-format §7) plus this document's rules for unit files. It names no
  agent-specific features.
- **Driver:** `pw.py strategy compile [--agent claude|codex] [--model M] [--full] [--milestone
  m1] --json`. It runs prepare, then calls the agent headless for step 2 (`claude -p` or `codex
  exec`) with `AGENT.md` and the work order, then runs assemble, verify, and report, and repeats
  the repair loop. It follows the lab's agent CLI contract (one JSON envelope, exit codes), so an
  autonomous loop can drive it.
- **Write scope is enforced by the driver, not by the agent's permission system.** The agent
  runs in a fresh, independent scratch git repository inside the staging directory, holding
  only its inputs (`AGENTS.md` = `AGENT.md`, `work_order.json`, previous units, and
  `context/`). After the agent returns, the driver compares a snapshot of that repository
  (including untracked and ignored files, HEAD, refs, and the index) with the one taken before;
  any change outside `units/<ID>.bas` for the listed IDs and `report_draft.json` fails the build.
  Nothing is reverted, and the user's checkout is never touched. This works the same for every
  agent. Writes outside the scratch repository are invisible to this check; only the agent's
  own sandbox limits them.
- **Wrappers:** a Claude Code subagent (`.claude/agents/pw-compiler.md`) and a lab skill
  (`paintbot-pw-compile`) for use inside a Claude session, and the matching `AGENTS.md` pointer for
  Codex. Each wrapper only points at `AGENT.md` and the driver.
- **Model and agent are recorded.** `version.json`'s `compiler` field records the agent (`claude`
  or `codex`), its CLI version, the model ID, and the hashes of `AGENT.md` and `LESSONS.md`. A
  default agent and model are set in one config file, so builds are comparable unless someone
  chooses otherwise.
- **Memory:** `strategy/compiler/LESSONS.md`, in the repo. It holds BASIC pitfalls the compiler
  has learned (for example: `NOT` binds tighter than `=`; `rnd` is a reserved name; division by
  zero disables the seat). The agent reads it every run and can propose additions in its report;
  a person or the edit loop accepts them by committing. It is in the repo, not in personal
  memory, so any agent reproduces the same build.
- **Context per unit:** the component's text, its previous unit (if any), the interfaces of the
  units it uses (from `map.json`: globals and SUB signatures), the relevant `policy-surface.md`
  sections, and `LESSONS.md`. Not the whole strategy file, which keeps the context small and
  the output focused.

## 10. Incremental builds

- `prepare` hashes each component's normalized text (fields that the compiler reads: `Spec`,
  `Params`, `Uses`, `Done when`, `Abort when`, `Log`; not `Rationale`, `Evidence`, or `Status`).
  A component is **changed** when that hash differs from `map.json`.
- A component is also rebuilt when a component it uses changed its interface (globals or SUB
  signature). `prepare` computes this from `map.json`.
- `--full` rebuilds every unit. Use it when the runtime skeleton changes or when drift
  accumulates.
- Rule tables, constants, and telemetry tables are regenerated every build; they
  are deterministic, so unchanged input gives unchanged output.

### M2 local audit implementation

`strategy_audit.py` exposes `pw.py strategy audit ROOT... --build ID --json`. The
implementation plan was reviewed with Claude Opus 5.5 before coding. It reuses the
existing telemetry parser, dense hash-verified replay loader, format parser and Python
selection reference. It reads the committed source and cross-checks the immutable map.
No policy, compiled BASIC, runtime telemetry, dependency or engine pin changes are needed.

Source-defined checks have identifiers `COMPONENT.N` in source order, with a separate
binding hash for their level, prose and Reads. Evaluators are reviewed Python, not LLM
judgments. Unknown predicates remain unmeasurable. Runtime and baseline semantic bindings
prevent a new source or runtime from silently inheriting an old model. The report keeps
all five levels, absent declarations, per-check coverage, exact evidence and raw outcomes.
Full conditional Results require belief truth and full execution evidence, including
skills; missing upstream declarations are not proof. Baseline private motor state therefore
blocks conditional Results without discarding observed pickups, survival or shot outcomes.
The [tool reference](../tools/pw_strategy.md#five-level-audit-m2-local) defines statuses,
selectors, identity checks, phase alignment, evaluator scope and evidence requirements.

Local validation uses the two M1 G5 recordings plus four full-length recordings (seeds
1–2, both sides) of the immutable baseline against `reference/base.bas`. These validate
instruments and lifecycle coverage; they are not hosted performance evidence. Before full
M2 acceptance, resolve the current league release, qualify the hosted telemetry path,
then obtain explicit upload/hosted-evaluation authorization. M3 must wait for M2 acceptance.

### M1 baseline decomposition

M1 preserves `reference/base.bas` at `coworld-v0.3.89`, including its original constants,
strict comparisons, tie order, integer arithmetic and memory across deaths. Its chosen source
layout is:

- Knowledge: self motion, visible contacts and previous motion, remembered supplies, and the
  derived squad assignment with local avoidance and idle-capture history. These update every
  tick, including ticks when supply or retreat overrides the movement goal.
- Situations and rules: retreat outranks resupply, which outranks taking or covering a heart;
  the legacy default goal is the fallback. Static roles split ring and cover seats. Commitment
  has no hold or priority margin.
- Capabilities: choose the corresponding goal and holding flag, call the common motor skill,
  then apply the original quiet-approach condition. They keep no activation-local tactical
  state, so switching rules does not reset baseline memory.
- One authored motor skill: baseline math, facing, footwork, dry routing, gun aiming and
  grenade timing. Objective selection, supply selection, retreat selection and sneak decisions
  remain LLM-compiled source components.
- Communication: routine literal status first, then the grenade announcement. Both are
  send-only; the comms v1 codec remains M3.

The layering rules forbid K→K and SK→SK calls. The pickup component therefore independently
checks for a visible carrier, and the motor helpers live in one skill. This introduces no new
behavior or format exception. Contact velocities are computed from old observations before
Knowledge advances its history; the motor reads those computed velocities. The pinned engine
reads frozen observations and keeps shouts separate from action commands, so sending the same
ordered shouts in the Communication phase preserves their gameplay effect.

The resumed preflight uses documented `doctor --offline`: the stored live teams league ID
returns 404, and its replacement runs 0.3.113. All local checks pass at the explicitly requested
0.3.89 pin. This is not a passed live-league check. Moving the pin and repairing live discovery
are required before later hosted work, outside M1's local scope.

## 12. Alternatives considered

| Alternative | Why not |
| --- | --- |
| Adopt a spec-driven toolkit (Spec Kit and similar) | Built for one-shot application features; no support for incremental regeneration of one file under per-tick budgets. |
| The LLM compiles everything, including rules and priorities | Less reliable where exactness is cheap; the rule table must match the audit's re-run of selection exactly. |
| One monolithic `policy.bas` rewritten each build | Large noisy diffs; no guarantee that a change stays local. |
| A custom harness on the Claude Agent SDK or Codex SDK | More to build and maintain for v1; both CLIs' headless modes, driven by a small Python script, already give the loop we need. |
| A Claude-only subagent and skill as the driver | Ties the process to one agent; the Python driver is agent-neutral and loop-drivable. |
| The local screen as a blocking gate for every build | Would veto behavior changes on the judgment of a self-play opponent; behavior changes are decided by hosted A/B (§8.2). |
| Builds kept out of git | Loses review diffs and the link from an uploaded policy to its exact file. |

## 13. Risks

- **The LLM writes BASIC that compiles but does not match the spec.** G4 blocks only builds that
  are not meant to change behavior, and even then catches gross regressions only. Mitigations: small per-unit context, `LESSONS.md`, the five-level checks in
  telemetry, and hosted A/B for behavior changes.
- **Interface drift between units.** A unit changes a global that another unit reads. Mitigation:
  `map.json` records interfaces, and `prepare` rebuilds dependents.
- **Budget creep.** Many small units can add up. G3 measures the whole file every build.
- **Local tools lag the league.** Gates run against the pinned engine; the pin must follow the
  league (`pw.py deployed-ref`).

## 14. Decisions (2026-09-30)

- Rules, priorities, Adaptations (priority changes), commitment, constants, telemetry tables, and
  the header are generated by Python. The skeleton, the telemetry print routines, and the comms
  codec are a hand-written runtime library, copied unchanged. The LLM writes neither.
- Builds are committed to git.
- Build ID `<source short SHA>-<n>`.
- The process ends at the local gate; upload and A/B use the existing skills with the build ID.
- The compiler is agent-neutral: a Python driver calls Claude Code or Codex headless with one
  plain `AGENT.md`, enforces write scope itself, and records agent and model; thin wrappers for
  each agent; an in-repo lessons file; no custom harness in v1.
- Telemetry v2 emission and its parser are built in M0-M1; M2 keeps the five-level audit and the
  hosted confirmation (James, 2026-09-30).
- Priorities are per rule in v1 (James, 2026-09-30).
- The local screen never vetoes a behavior change. It blocks only builds that are not meant to
  change behavior, the M1 milestone, and any build with a bad seat.
