Design Plan · 2026-09-29 · Proposal for review

Paintbot PW: tooling and skills plan

This plan lists each tool and agent skill that the Paintbot PW lab must have to diagnose, test, and improve our BASIC policy, and it tells how to get each one. We did the research against paintbot-pw 0ff41d2d (tag coworld-v0.3.77, rules 47). The league used that build on 2026-09-29.

Executive Summary

The engine makes this work unusually cheap. A hosted replay is a complete record of the actions, with a state hash for each tick. The engine already has hooks (observeShot, observeHit, observeTag, and, with -d:pwTraining, also damageObserver/damageWeapon). When a tool plays a replay again with those hooks and reads the World fields in each tick, it gets every event that we asked for. That includes shots, hits (with the attacker, the victim, the weapon, and the distance), damage to armor and to HP, kills, respawns, pickups, the start, pause, reset, and end of each capture, glory by type, the text of each shout, disguises, and each entry into a trench or into water. It also gets the full state in each tick, which the movement diagrams use. A scratch probe did this on all three sample league replays with zero hash errors. It took 0.5–1.0 s for each match for events, or 2.7–4.5 s for each match with all-pairs visibility1. Only four items need an engine patch or our own logs: the exact result of a gun ray that gets to a victim with spawn protection or a trench dodge, the intended target of a shot, why and when a VM stopped, and the internal intent of the policy. A native library also runs local 16-seat BASIC matches with the exact rules and glory configuration of the league, at approximately 5.4 s for each match. Its hashes are the same as those of the headless binary1. The sibling labs already solved the hard parts of the analysis: the Gods of the Arena chain from episode reader to A/B adapter to miner features, the shared coworld-ab statistics engine, and the survey and field-study practice of crewrift2.

Key finding · the ladder now rates glory margin One result of this research changes what we must measure. Since the evening of 2026-09-28, the paintbot-pw ladder rates each episode by the glory margin, not by win, draw, or loss. The live league settings have margin_scale: 10003. Thus the Elo outcome of an episode is clamp(0.5 + (our glory − their glory) / 2000, 0, 1)4. A 500-glory win counts 0.75, a 950-glory win counts approximately 0.98, and a zero-glory win counts as a draw. Thus the size of the glory now changes the rank. This is the opposite of what the lab docs and the onboarding report said, and T0 corrects them. The change also helps the A/B test: this outcome score is continuous for each episode, so a test needs fewer episodes than a simple win or loss.

The plan has fifteen tools plus a currency repair (T0–T15) and six lab skills, in five phases. All of them go in the Paintbot PW lab, except two game-agnostic statistics additions to the shared coworld-ab skill. Phase 0 does a new check of the lab docs at rules 47, because they are two releases old. Phase 1 makes the base that all other parts read: a trace tool with a hash check (pw_trace), an episode reader with a signed cache, and Parquet tables for each type of event that DuckDB can query. Phase 2 is the A/B set: a compare.py adapter, the paired and sequential (SPRT) tests that coworld-ab does not have today, a local batch harness, and the paintbot-pw-ab skill. Phase 3 gives movement diagrams and a report for each match on a real terrain background. Phase 4 gives opponent scouting, fight and trade metrics, and the hypothesis-miner adapter. Phase 5 has the ideas that need more work: credit from a win-probability model, intent telemetry and belief audits, and the tuning of constants. James must make four decisions: the default A/B design, whether to add SPRT to the shared engine, the telemetry budget that our BASIC can use, and whether the optional rerun viewer is a permitted dependency.

1 · Problem and goals

  • The lab has no analysis instruments yet. It has only a release resolver and a pinned engine build.
  • James asked for an A/B skill, a full unpack of each replay, movement diagrams, and the primary combat and objective metrics.
  • Each number must be correct, quick to get, easy for a person to see, and pinned to a release.

The lab has no instruments yet. It has only deployed_ref.py, which finds the release and commit of the league, and build_tools.sh, which builds the pinned engine5.

James asked for five items. The first is a good A/B skill. The second is a tool that unpacks a replay to get every event. The third is movement diagrams for a time span that he selects. The fourth is measurements of accuracy, deaths, damage dealt and taken, score, glory, and nearness to hearts. The fifth is any other useful item, with ideas from the other labs.

Goals

  1. Correct numbers. Each number has a hash check, and no data disappears without a record.
  2. Fast iterations. The lab rule is speed first, and the number of iterations each day is the measure6.
  3. Behavior that a person can see and judge.
  4. Use of the shared engines and of the patterns of the sibling labs.
  5. A version pin on everything, because the game releases many versions each day.

Non-goals

  • A new build of the web replay viewer. That build needs Emscripten and a private art repository1.
  • Heartland. It is now a separate coworld with heartland-v* tags, and it is out of scope.
  • A Python Flatty decoder. The Nim loader already validates the format and records its version.

3 · Design principles

  • The plan has eight principles, and each one comes from evidence in the engine or in a sibling lab.
  • The primary idea: one replay run with a hash check supplies all data, and no data disappears or mixes across versions.
  1. One source of truth with a hash check. Each number comes from a new run of the replay, and that run stops with an error when a hash does not agree14,2.
  2. The replay tells what occurred, and telemetry tells why. The tape already has each command that each seat executed, and the new run gives the results for all 16 seats. Thus our BASIC prints only its intent1,2.
  3. The unit is the episode, with one row for each (episode, policy). Eight seats of one policy in one episode are not eight samples. The ctf-ab tool and the GotA miner made this mistake2.
  4. Exact values and inferred values never mix. An unknown value is null, not zero, and the tool counts and prints each exclusion15.
  5. Everything has a version pin. Tools build at the release of the recording, each result records its coworld_version, and a comparison never mixes two versions of the rules16.
  6. Use what exists before you make something new. Use the shared engines for statistics and mining, the Nim engine of the repository for simulation, and only the Python dependencies that the project has now. pandas, pyarrow, DuckDB, matplotlib, scipy, Pillow, numpy, and scikit-learn are already in the project17.
  7. Output that agents and people can both read. Each report writes JSON next to its HTML or PNG2.
  8. Local runs are for mechanisms and screening, never for evidence against the field. The cue_n_woo lab had to learn this lesson again and again, and it is a lab rule18.

4 · Architecture

  • The design has five layers: sources, then a trace with a hash check, then Parquet tables, then one metric library, then the consumers and skills.
  • All consumers read the same tables, so each metric has only one definition.
  • In the policy, one intent telemetry line in our BASIC, controlled by a setting.

T1pw_trace: hash-checked replay expander (Nim)

Phase 1 · Effort M (≈ half a day)

Purpose
Unpack a replay into every event and the full state for each tick.
How it's built

Move the verified scratch probe (pwtrace.nim)1 into the lab tools as pw_trace.nim. Compile it in the release worktree, as GotA copies its .nim file into the engine tree19,2, and add it to build_tools.sh. Flags: -d:pwTraining -d:headless --threads:on.

The hooks and sources are these1. observeShot gives each shot20. observeHit gives each hit, before armor removes damage20. observeTag gives each kill20. damageObserver and damageWeapon give the damage and the weapon20. Differences in the World between ticks give the windup, spray bursts, the charge, throw, and blast of each grenade (w.grenades, w.blasts), pickups (jumps in pickups[k].readyAt), captures (heartCaptures, controlHearts.owner), glory (w.gloryEvents), the cogs that take glory hearts (w.gloryPickups), disguises (w.uniforms), entries into and exits from trenches and water, and spawns. The tool removes duplicate glory events by (tick, team, kind, amount), because hearts pay before the tick counter increases. Commands and shouts come from the tape (recording.communications).

Output

Schema v1 has these rows:

  • A meta row (episode, rules, seed, seats, names, configuration, binary sha)
  • event rows (tick, kind, seat, other, x, y, weapon, amount, …)
  • state rows every N ticks (default 6, which is 4 Hz) with positions, aim point, goal, hp, armor, lives, alive, charge, in_water, and trench, and every tick for a window that you ask for
  • Optional visibility sets every M ticks (these cost approximately 1 ms for each tick for all pairs)
  • A summary row (final hash, ticks, glory, meter, per-seat counters).

Rules: if a hash does not agree, the tool stops with a non-zero exit code and writes a failed summary. The tool runs one process for each replay, because the engine uses global variables21. It uses seq/MaxSeats in all places.

Known gaps, which the tool records as null values with a flag: a ray that gets to a victim with spawn protection or a trench dodge looks like a miss. The tool approximates these cases from the geometry of the ray. An exact answer needs a hook in the trench-dodge code20. The tick when a VM stops is available only from our own logs, or from a test for "all commands are zero while the cog is alive".

Cost: 0.5–1.0 s for each match for events, 2.7–4.5 s with full visibility, and 128–216 KB of event JSONL for each match1.

Verification
Identity checks: the sum of the glory events (without duplicates) plus the countdown is equal to the final glory of the team. The ticks, scores, and seed in results.json agree. The number of kills is equal to the sum of SeatStats.kills. Run the tool on the 3 sample replays and on one new hosted rules-47 replay. We did not do that last check yet: hosted builds use Nim 2.2.10, and our build uses 2.2.6.

T2pw_episodes.py: episode reader, trace cache, tables

Phase 1 · Effort M (≈ half a day)

Purpose
Change a directory of episodes into cached tables with correct joins, which each metric, report, and test reads.
How it's built

The model is gota_episodes.py22 and replay_stats.py23 from GotA2. The tool reads episode.json and results.json. It finds the tape under each name that the fetcher can use, and it identifies the POLYWORLDREPLAY magic and gzip. It runs pw_trace at the release of the recording (from the rules and coworld version in the replay header). It keeps the output in a cache with a receipt signed over the sha256 of the replay, the results, episode.json, the binary, and the options. It moves the output into place in one atomic step. It lists each failure and stops with exit code 1.

The tool joins seats by position, never by the sequence in an array. The team comes from game_config.slots/participants, with a parity check that stops with an error when they do not agree2. The policy identity comes from the exact policy_version_id.

The tool also reads our seat logs: intent lines (T13), BASIC error: lines as vm_error, and the oracle journal if the policy uses the oracle.

Output
Parquet tables (pyarrow) for each episode, in a layout like awpy24: episodes, seats, shots, damage, kills, spawns, pickups, captures, glory, shouts, states (sampled), visibility (optional), and policy_log (our intent lines). A batch is a directory, and DuckDB views over all Parquet files in it answer questions as they occur.
Verification
The cache works correctly for hits and misses, and the tool lists each failure.

Phase 1 · Effort M (≈ half a day)

Purpose
One definition for each metric. Thus the A/B test, the reports, and the miner always agree about the meaning of a number.
How it's built
The library calculates each metric from the T2 tables at three levels: seat, (episode, policy), and team. The catalog is in §8.
Output
Each metric has units and a denominator. It is null when its input is missing.
Verification
We compare samples of the metrics with the per-seat counters of the probe.

T4pw_fights.py: engagements, trades, openings

Phase 4 · Effort M (≈ half a day)

Purpose
Describe fights, not only separate hits: who fought whom, who won, and what the fight cost.
How it's built
The tool divides hits and kills into engagements by time and distance. By default, events within 48 ticks and 1,500 units are in one engagement, and we will examine these values again after the first batch. This follows the OpenDota teamfight idea and the space-time graph in find_firefights.py from ctf24,2. A trade is a kill that a teammate avenges within 72 ticks (the CS2 practice, and a default value). The tool also finds the first duel of each heart contest and the time from the first sighting to the first hit, which needs visibility samples.
Output
For each engagement: the participants as N against M, who saw first, who hit first, the winner, and the hearts that the fight changed. Also trades, first duels, and the time to the first hit.
Verification
The plan gives no separate check. We will examine the default values again after the first batch.

T5compare.py: coworld-ab adapter

Phase 2 · Effort M (≈ half a day)

Purpose
Send Paintbot PW episodes into the shared A/B engine with the correct unit, groups, and primary metric.
How it's built
The frame comes from compare.py in the original Paintbot lab (rows for each episode, exact version selection, groups for each version and side)25. It also uses the exclusion counter and ops_fail_rate from GotA2. The groups are red, blue, all, and one group for each opponent. The primary mean metric is the Elo outcome score of each episode. Rate metrics are binary for each episode (win, draw, win with zero glory, first capture). The other mean metrics are averages over our 8 seats in each episode.
Output
Results through render_markdown/emit_json. The tool keeps them together with the request ids and request bodies that made them (a sugarscape practice, and a gap that the player_ade analysis found)2.
Verification
Contract tests.

T6Paired and sequential statistics: shared, game-agnostic

Phase 2 · Effort S/M · Root change, needs James's go-ahead

Purpose
Give coworld-ab the tests that it does not have. Thus matched designs and early stops are statistically correct.
How it's built
We add these items to the shared coworld-ab scripts:
  • (a) A paired test for designs where the two arms share seeds, sides, and opponents: a paired t-test on the difference in outcome score for each pair, with a Wilcoxon signed-rank check, and McNemar on discordant pairs for the win rate.
  • (b) A head-to-head test: a one-sample t-test of the outcome score against 0.5, and an exact binomial test on decisive games, for each side.
  • (c) A sequential probability ratio test on the mean difference in outcome score, as the GSPRT of Stockfish fishtest does for Elo24.
This is a game-agnostic root change, so James must approve it.
Output
New test paths in the shared engine, which all labs can use.
Verification
The new paths keep the existing safeguards. A "significant" verdict needs a minimum of 30 episodes in each arm (SMALL_N = 30). Benjamini-Yekutieli correction applies across the reported metrics. The tool counts exclusions and reports operational failures as a metric. Each safeguard has a contract test, in the style of the shared analysis-contract tests26.

T7pw_local.py: local batch harness

Phase 2 · Effort M (≈ half a day)

Purpose
Run many local matches quickly for compile checks, mechanism checks, and screening. The results are never evidence against the field.
How it's built
The harness controls the native library (native_env.nim, built with --app:lib -d:pwTraining)27 through ctypes. It sets pw_set_rules(47), pw_set_config_json with the glory configuration of the league, 16 seat scripts, and the seeds. pw_results gives the winner, glory, meter, and hearts1. It runs parallel processes on all cores. We estimate approximately 2.5 matches each second, but we did not do a load test.
Output
Uses: a compile check of a candidate in seconds, mechanism checks, screening against base.bas and our older versions with side swaps, and records of selected matches with paintbot-headless --record for T1.
Verification
Parity guard: before you trust a batch, compare some final hashes with the headless binary (they were the same on seeds 7–9). The harness refuses to run if the build of the library is not from the target release. The idea of this guard comes from render_topology.py in the original Paintbot lab2.

A real terrain background for movement diagrams and heatmaps.
How it's built
An exporter of approximately 40 lines takes samples of terrainHeight, inWater, blocked, and trenchAt on a grid from newWorld. It also writes JSON with the bounds, hearts, pickups, trenches, cover, and homes1. Generated maps come from their .pbmap grids.

T9pw_viz.py: movement diagrams and charts

Phase 3 · Effort M (≈ half a day)

Purpose
Show behavior: where the cogs went in a time window that you select, where they die, and how control changed during the match.
How it's built

The tool draws movement trails for a tick window that you select (--from/--to in ticks or seconds, --seats, --team, --policy) on the T8 terrain. Each seat gets one line, which breaks at death and respawn. Arrowheads show the direction. Markers show the events in the window: kill ×, death ○, capture ◆, pickup ▲, a ring for each grenade blast, and short rays from the shooter for shots. The color of each heart shows its owner at the end of the window.

Small multiples show the same window across some episodes, or for each opponent. Batch heatmaps show where cogs spend time and where they die (hexbin or KDE24). A comparison of occupancy for each policy gives an overlap score, as the Bhattacharyya overlap in heat_compare.py of crewrift does2. Timelines show the meter and glory of each team over time, with the ticks of captures and kills, and a strip that shows the owner of each heart ("control over time"). An optional animated GIF of a window uses matplotlib and Pillow, because this machine has no ffmpeg.

The tool uses only matplotlib, which is already a dependency.

Output
PNG files, plus JSON of the plotted data.
Verification
A visual comparison of one known moment with the web viewer.

T11pw_scout.py: opponent scouting and field survey

Phase 4 · Effort M (≈ half a day)

Purpose
Learn what the leaders do, from public league episodes, with no cost in credits.
How it's built

The tool makes a policy×policy win matrix with Wilson intervals, as crewrift-survey does29. This matrix fits well here, because each episode has one policy on each team. For each opponent, a profile shows the first routes and first heart targets (the idea of infer_battle_plan.py from ctf, but with the team from the metadata, not from parity), the sequence of hearts, the weapons, the use of grenades and spray, the pickup habits, the usual time to win, the parts of the glory, and their shout protocol. The shout text is in the tape, and we can read it (for example, FIRE22 1137 1763 in a sample)1. A shout also gives the exact position of the speaker to all cogs within 12.8 m, and that includes our cogs.

Field-study practice, from crewrift-field-study30: before you pull a batch, put one new replay through T1. If a total is exactly 0% or 100%, think that it is a tooling bug until you prove otherwise.

Output
The matrix, the opponent profiles, and flagged episodes, each with a one-line reason that an agent writes (the reasons.json of crewrift-survey).
Verification
The check of one new replay before each batch pull.

T12pw_flags.py: anomaly flags

Phase 4 · Effort S/M

Purpose
Show a person or an agent the exact ticks where something went wrong.
How it's built
The tool makes flags from rules, each with its tick. The flags are:
  • Cogs that are stuck or move back and forth (the same goal and a small displacement)
  • Alive seats that do nothing (all commands are zero, which is also the test for a stopped VM)
  • A death alone in enemy vision
  • A heart lost while allies were near
  • A grenade with no victims
  • Hits on teammates
  • Long time in water (72 ticks or more)
  • Wins with zero glory.
Defaults: "stuck" means the same goal and a displacement of less than 200 units over 72 ticks while alive. "Idle" means all commands are zero for 48 ticks or more while alive. Each threshold is a named constant in one place.
Output
Flags with ticks, and the report shows the thresholds. The tool sorts our losses by margin, and we examine the worst loss first (the Halite triage method)24.
Verification
The plan gives no separate check. Each report shows the thresholds, so a reader can judge them.

T13BASIC intent telemetry + parser

Phase 2 (in the first policy) · Effort S (≤ 2 h)

Purpose
Record why our policy did an action. The replay cannot tell us this.
How it's built
A maximum of one short line for each decision, controlled by a configuration setting. The line records only intent: the mode, the selected heart, the target seat, a reason code, and the remaining instruction budget. Budget: a maximum of 1 print for each decision and approximately 200 bytes. That is much less than the limit of 1,024 bytes and 128 events for each decision. If a policy goes over that limit, the seat stops8,31. The average must also stay below approximately 700 bytes for each tick, so that a full match stays under the 10 MiB log limit1. The policy writes the line when the intent changes and also every N ticks, as the LH line of GotA does2. T2 contains the parser.
Output

7 · The A/B design

  • Primary metric: the continuous Elo outcome score, which the ladder itself uses.
  • Recommended default: one common opponent, with paired seeds and sides.
  • Stop with SPRT as episodes arrive, or at a fixed N without early looks.

Unit and outcome

The unit is one episode, which has two policies, one on each team. The primary metric is the Elo outcome score that the ladder itself uses, clamp(0.5 + (our glory − their glory) / 2000, 0, 1). This is a continuous value for each episode4, because the live setting is margin_scale: 1000. If an episode fails and the platform connects the failure to one policy, that side gets 0 or 1 (the forfeit branch)4. The secondary metrics are the win rate (a draw counts as no win), the time to win, the parts of the glory, the wins with zero glory, and heart-seconds, which is a margin measure with less variance.

Three designs

Design 1 · Recommended default

Common opponent, paired seeds and sides. The candidate and the baseline each play the same opponent policy, with all 8 opponent seats pinned to one explicit policy_ref. They use the same list of seeds and both sides. We pair the episodes by (seed, side). A paired t-test on the difference for each pair tests the primary outcome score, and a Wilcoxon signed-rank test checks the result. McNemar on the discordant pairs tests the win rate. A draw counts as no win, and a pair with the same result in both arms is concordant and the test does not use it. This design answers the question "is it better against X". Do it again for each leader, and combine the results, with a report for each opponent.

Design 2

Head-to-head. The candidate plays the baseline in the same episode, and the sides change across the batch. A one-sample t-test compares the outcome score of the candidate with 0.5, and an exact binomial test on decisive games gives the win-rate view, with a report for each side. This design gives the most information for each episode. But a change can win against our old version and still do worse against the field (the "Just Woke Up" warning from Battlecode)24.

Design 3

Field sample. Both arms play a mix of the current leaders, without pairs. The Fisher and Welch tests of coworld-ab apply, as they do today. This design is the nearest to the ladder, and it costs the most.

Stopping and scale

The stop rule is a sequential probability ratio test on the mean difference in outcome score (a normal approximation, as the GSPRT of fishtest does for Elo). An example is H0 = 0 against H1 = +0.05 with α = β = 0.05, with a check as episodes arrive. The alternative is a fixed N without early looks.

Scale: for the win-rate view, the guide estimates approximately 250 episodes to separate a 62% win rate from 50%35. The continuous outcome score needs fewer episodes, and we will measure how many on the first batch. At approximately 0.3 credits for each episode, that is approximately 75 credits for each arm, from a balance of 20,000 credits that increases by approximately 1,429 each day36.

Variance control

League episodes use game_config.seed 2026. We do not know yet if the engine seed changes for each job (an open question). If we pair by explicit seeds through game_config_overrides.seed, we can compare the arms in both cases.

Guardrails from the sibling labs Use a minimum of 30 episodes for each arm in each group before a "significant" verdict. Use BY correction across the reported metrics. Count the exclusions. Report operational failures as a metric. Never mix two versions of the rules. Do a new confirmation run before you accept an effect that the miner found2,24.

12 · Alternatives considered

  • Eight alternatives. For each one, the section tells why we rejected it, put it on hold, or used a lighter form.
  • The common reason: the Nim engine is the only correct source, and new dependencies wait until we clearly need them.
Rejected · Python Flatty decoder of tapes

What: decode tapes in Python, as replay_actions.py of GotA does41. Why not: it cannot prove that the replay is deterministic, and it cannot give results. The Nim engine is the only correct source.

Adopted in lighter form · Warehouse first

What: make the DuckDB + Parquet warehouse of crewrift and ctf the center of the design. Why not as proposed: it is heavier. Parquet tables for each episode with DuckDB views give the same storage without a separate build step.

Deferred · Engine patch for exact shot outcomes

What: add a hook in the trench-dodge code20. Why not now: the patch is small, but it makes a fork of a repository that has many releases each day. Start with an approximation from geometry and with flags. If the gap is important, ask the maintainer for the hook.

Rejected for now · Counterfactual branch-from-tick

What: branch a replay at tick T and continue the play (the "Take Command" feature of StarCraft). Why not: after tick T, the recorded commands of the opponents do not fit the changed world, and their BASIC is private. Also, the globals of our VM start again empty. The method is correct only for a small number of ticks.

Rejected · Building the web viewer locally

What: build the replay viewer for better playback. Why not: it needs Emscripten and the private polyworld_art checkout42. Links to the hosted viewer give what we need.

Deferred to Phase 5 (optional) · rerun.io scrubbable timeline

What: a rerun.io timeline for per-tick debug work24. Why not now: it is good for per-tick debug work, but it is a new dependency. Offer it as an option in Phase 5, after the matplotlib panels exist.

Rejected · Local batch results as evidence

Why not: a lab rule. Local runs are only for screening.

Rejected · Reusing the shared coworld-local-run skill

Why not: it operates only with Docker, and this game has no player container.
