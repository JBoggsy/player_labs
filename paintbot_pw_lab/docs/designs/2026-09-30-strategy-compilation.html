Compilation of the strategy file to BASIC

A process that turns the committed strategy file into the plain BASIC file that the league runs for each seat. Each build has a version record, a compile report, and local gates.

Executive Summary

The strategy file is the only artifact that we edit, and the process makes the BASIC from it. Spec-driven development calls this model spec-as-source (§3). The process turns the committed STRATEGY.md into the plain BASIC file that the league runs for each seat. Python does every step that it can do exactly: the lint, the hashes, the rule table, the constants, the telemetry tables, the assembly, and the gates. One LLM agent writes BASIC only for the components whose text changed. A small Python driver runs the process and calls Claude Code or Codex headless for that step. Each component becomes one unit file, thus a change to one component changes one unit.

Each build has an ID, a version.json record, and a compile report. The record links the build to its source commit, its compiler, and its gate results. The report lists every guess that the compiler made, thus the edit loop can resolve each guess in the source. Five local gates do checks of lint, compile, budget, a local screen, and telemetry. The local screen plays the build against a reference in the native engine on this machine. It is screening only: it finds a broken or clearly worse build, but it cannot show that a build is better in the league. Thus the local screen never vetoes a behavior change. A hosted A/B decides each behavior change (§8.2).

1 · Problem

  • STRATEGY.md is written in precise natural language. The league runs one plain BASIC file for each seat.
  • We need a process that turns the first into the second.
  • The process must change only what changed, record its guesses, and make each build traceable.

STRATEGY.md is the source of truth for our policy, and we write it in precise natural language. The league runs one plain BASIC file for each seat. We need a process that turns the first into the second. The process must obey these requirements:

  • It makes BASIC that compiles, stays inside the per-tick budgets, and logs telemetry v2.
  • It changes only the BASIC for components whose text changed.
  • It records every guess that it makes, thus the edit loop can resolve each guess in the source.
  • It makes every build traceable to its exact source, compiler, and verification results.
  • It operates inside a session, or unattended in an autonomous loop.

2 · Goals and non-goals

  • Python does all work that it can do exactly. One component gives one unit file.
  • Each build names the source and the compiler that made it. A small build takes minutes.
  • Not in scope: byte-identical recompiles, upload and hosted evaluation, and a custom agent harness.

Goals

  • Reliable where it can be exact. Python does all work that it can compute deterministically. The LLM does not do this work.
  • Modular output. One component gives one BASIC unit file. A change to one component changes one unit.
  • Reproducible record. A build names its source commit, compiler model, compiler instructions, and lessons file.
  • Fast. A small incremental build, with verification, takes minutes.

Non-goals

  • Byte-identical recompiles. Two LLM runs can make different BASIC from the same text. We accept this (strategy file format §9)1.
  • Upload, league submission, and hosted evaluation. The process stops at the local gate. The current skills (paintbot-pw-ab2 and the upload skill) take a build ID from there.
  • A custom agent harness. v1 calls a current coding agent headless (Claude Code or Codex) from a small Python driver.

3 · Prior art

  • Spec-driven development is an established category. Our model is the spec-as-source variant.
  • We borrow three ideas: validate first, one written contract, and an ID for each item.
  • We do not adopt a toolkit. Our pipeline is small and specific.

Spec-driven development is an established category3. In one variant, people edit only the specification, and a tool makes the code from it. This variant has the name spec-as-source34, and it is our model. The best-known toolkit is GitHub Spec Kit. It uses Markdown specifications, validation, and generation through any LLM5.

We borrow three ideas:

  • Validate the specification before generation.
  • Keep one written contract that the generator obeys.
  • Give every item in the specification an ID that code and tests trace to.

We do not adopt a toolkit. The toolkits are for one-shot application code, one feature at a time. They do not handle incremental regeneration of a single BASIC file under hard per-tick budgets and a fixed runtime skeleton. Our pipeline is small and specific. Thus a few hundred lines of Python and one instruction file cost less than the adaptation of a framework.

4 · Architecture: deterministic steps around one LLM step

  • Five steps. Python does four of them.
  • Only step 2 (Generate) uses an LLM, and its input is small.
  • A Python driver, pw.py strategy compile, runs all five steps and owns the process. Any supported agent can do step 2.
  • Python makes the rule table, constants, telemetry tables, and header, because exact code is testable. A hand-written runtime library holds the skeleton, the telemetry print routines, and the comms codec.
StepDone byWhat it does
1. PreparePython: pw.py strategy prepareRefuse uncommitted source. Lint STRATEGY.md. Hash the source. Compare the component texts with the map.json of the previous build, and list each component as new, changed, unchanged, or removed. Write a work order for the agent.
2. GenerateLLM compiler agentWrite one unit file for each new or changed component (Knowledge, Situations, Capabilities, Communication). Record guesses.
3. AssemblePython: pw.py strategy assembleCopy unchanged units from the previous build. Copy each skill.bas unchanged. Copy each runtime library unit unchanged. Make the rule table, the constants block, the telemetry code tables, and the header. Join everything into policy.bas in the fixed per-tick order. Write map.json and version.json.
4. VerifyPython: pw.py strategy verifyDo the gates (§8). If a gate fails, the agent gets the error and repairs its units, for a maximum of 3 rounds.
5. ReportPython + agentWrite report.json and report.md (§7).

A Python driver, pw.py strategy compile, runs all five steps and calls the agent for step 2 (§9). The driver owns the process, and the agent does not. Thus any supported agent can do step 2.

Only step 2 uses an LLM. Its input is small:

  • The work order.
  • The text of the changed components.
  • The previous unit files of those components.
  • The interfaces of the units that they use.
  • docs/policy-surface.md6.
  • compiler/LESSONS.md.

4.1 What the LLM does not write, and why

Made by PythonReason
Rule table from ST.rules (conditions, priorities, capability calls, roles)The rule syntax is structured (R.id [priority]: WHEN ... DO ...). Deterministic code is exact and testable. The "acted properly" audit also needs it, because the audit does the rule selection again from logged inputs.
Adaptations table from A. componentsThe same reason, when an Adaptation is only a change of priority. If the condition of an Adaptation needs new logic, the LLM writes a condition unit for it. The change of priority stays generated.
Commitment logic from ST.commitment parametersMinimum hold, preemption margin, and hysteresis are numbers that apply to the rule table.
Constants block from all ParamsOne init block. Each tunable parameter gets ' @tune min max step7.
Telemetry code tables (made by Python)The codes for every ID go into map.json and into the script as constants.
Runtime library (hand-written in compiler/runtime/, copied unchanged): the per-tick skeleton, the telemetry v2 print routines, and the comms codec for the wire format of strategy/comms.md8This code is fixed: the per-tick order, a print budget that we check one time, and exact arithmetic (packing, check, scrambling). We write and review it as we do skill.bas. LLM-written COM. units decide which message to send and what a received message does.
Header (made by Python)The build ID, the source commit, and "generated, do not edit". The per-tick order that the skeleton obeys is in the strategy file format §31.

5 · Build layout

  • The source, the compiler instructions, configuration, memory, and runtime, and one directory for each build all live under strategy/.
  • We commit builds to git.
  • Unit files describe themselves. The runtime units are authored source, like skill.bas.
paintbot_pw_lab/strategy/
  STRATEGY.md, skills/, comms.md            # source (edited by the edit loop)
  compiler/
    AGENT.md                                # compiler instructions, agent-neutral
    config.json                             # default agent and model
    LESSONS.md                             # compiler memory, reviewed like code
    runtime/                                # hand-written library units: skeleton, telemetry, comms codec
  compiled/
    <build-id>/
      units/<ID>.bas                        # one per component (generated or copied)
      policy.bas                            # assembled upload file
      map.json                              # ID -> unit, code, globals prefix, text hash, log fields
      version.json                          # §6
      report.json, report.md                # §7
      verify/                               # gate outputs: compile.json, peaks.json, screen summary
    uploads.jsonl                           # append-only: build-id -> uploaded policy ref, date
  • Build ID: <source short SHA>-<n>, for example a1b2c3d-2. n counts the builds of the same source commit.
  • Builds are committed to git. They are small text files, and their diffs are worth a review. Also, the uploaded artifact stays recoverable.
  • Unit files describe themselves. Each unit file starts with a comment that gives the component ID, the hash of the source text, and "generated, do not edit". The globals of each unit share a prefix that comes from its ID, and map.json records the prefix. Thus units cannot collide.
  • compiler/runtime/ is authored source, like skill.bas. People write and review it by hand, and the build copies it unchanged.

6 · Versioning

  • The compiler makes a build only from committed source.
  • version.json names the source, the compiler, the engine, and the gate results.
  • Uploads go into an append-only log, thus a build directory never changes after the process writes it.

The compiler makes a build only from a committed STRATEGY.md, skills/, and comms.md (compile contract item 2)1. Each build writes version.json with these fields:

FieldMeaning
build_idThe build ID (§5).
source_commitThe git SHA of the source.
source_hashessha256 of STRATEGY.md, comms.md, every skill.bas, and every runtime unit.
previous_buildThe build ID that the incremental step used, or null for a full build.
compilerThe agent (claude or codex) and its CLI version, the model ID, the sha256 of AGENT.md, and the sha256 of LESSONS.md.
engineThe coworld tag and commit that the gates used (tools/release.env)9.
policy_sha256sha256 of policy.bas.
gatesPass or fail for each gate (§8).
createdDate and time.

Uploads add a line to compiled/uploads.jsonl (build_id, the policy ref name:vN, and the date). Thus a build directory never changes after the process writes it. The link from a league policy version back to its source is: policy ref → build ID → version.json → source commit.

7 · The compile report

  • Two files for each build: report.json for loops and report.md for people.
  • Each guess has a stable ID, a severity, and a state.
  • Guesses carry forward from build to build. An open guess of severity high blocks Status: tested for its component.

Each build has two report files: report.json for loops and report.md for people. The report has these contents:

  • Units: each component, with the status new, changed, reused, or removed.
  • Guesses: one entry for each place where Spec was ambiguous or not possible. The table below gives the fields.
  • Gaps: each thing that the spec needs and the engine does not give, with the substitute that the compiler used.
  • Gates: the result of every gate, with numbers.
  • Budget: the peak instructions, work units, and print use per tick.
FieldMeaning
idA stable guess ID, G-<component>-<n>.
componentThe component ID.
spec_quoteThe exact text that the guess reads.
decisionWhat the compiler implemented.
whyThe reason for that decision.
severitylow (a detail), medium (changes behavior in some situations), or high (the spec is contradictory or not possible).
stateopen, possibly resolved (the text of the component changed since the guess), or closed (the edit loop confirmed it).

Guesses carry forward from one build to the next. The edit loop closes a guess when it changes the component. It can also record in STRATEGY.md that the guess is the intended behavior. The next build then shows the guess as possibly resolved, and the edit loop makes it closed. Any open guess of severity high blocks Status: tested for its component.

8 · Verification gates

  • Five gates operate locally against the pinned engine.
  • On a G2, G3, or G5 failure, the agent repairs its units, for a maximum of 3 rounds.
  • G4 never starts a repair, because "worse" is a strategy question. A bad seat always fails the build.
  • The local screen is screening only. It finds broken or clearly worse builds, not better ones.
  • The local screen never vetoes a behavior change. For a behavior change, G4 is advisory (§8.2).

All gates operate locally against the pinned engine (tools/release.env)9.

On a G2, G3, or G5 failure, the agent gets the error and repairs its units. After 3 failed rounds, the build stops with a failed report. G4 never starts a repair, because "worse" is a strategy question. A bad seat (a crash or a disabled seat) in G4 always fails the build.

8.1 What the local screen is

pw.py local screen A.bas B.bas --seeds 1-28 plays A against B in the native engine of the game on this machine10. It uses the rules and glory settings of the league. The screen plays every seed two times: first with A on the even seats, then with A on the odd seats. This cancels the side advantage. The result is 56 matches in approximately 20 seconds with the terrain cache of the lab.

The screen reports these results:

  • seed_balanced.mean_outcome: the mean Elo outcome score of A (clamp(0.5 + (A glory - B glory) / 2000, 0, 1))12. The screen first calculates the mean of both sides for each seed, then it gives the mean with a 95% confidence interval. A policy against itself scores exactly 0.5.
  • bad_seats: each seat that did not compile, or that the engine disabled during the match.
  • identical_play: true when the two files played identically, move for move.
  • Per-seat stats: damage, hits, kills, deaths, captures, and first friendly fire.
Screening only The local screen is screening only. The only opponents are the files that we seat, the LLM oracle is off, and the seeds are not the seeds of the league. The screen answers the question "is this build broken or clearly worse?" It never answers the question "is it better in the field?" The hosted A/B skill (paintbot-pw-ab) answers the second question2.

8.2 The local screen never vetoes a strategy change

The previous build is a weak judge of a behavior change. It can use a weakness that exists only against itself. Also, play is not transitive. A build that loses to the previous build locally can still do better against the league field. The reverse is also possible.

Principle A behavior change is decided by a hosted A/B, never by the local screen.

Thus the G4 outcome rule depends on the intent of the build. prepare finds the intent from the source diff. G4 compares the new build (A) with a reference (B):

Build intentHow prepare knowsReferenceG4 outcome rule

No behavior changeNothing that the compiler reads changed. Examples: a --full recompile, or a change to the runtime library, LESSONS.md, the agent, or the engine pin.The policy.bas of the previous buildBlocking. ci95_high >= 0.5. A clear regression here means that the compiler or the runtime broke something.

In every case, a bad seat fails the build. A behavior-change build can score clearly below its previous build. Then the report gives it a prominent note, thus the edit loop sees it before the hosted A/B. The build is not blocked.

9 · The compiler agent

  • The compiler works with both Claude Code and Codex. All important parts are plain files and a Python driver.
  • The driver calls the agent headless and enforces the write scope with a git check.
  • Each build records the agent and the model. The compiler memory is LESSONS.md in the repo, and the context for each unit stays small.

The compiler works with both Claude Code and Codex. All important parts are in plain files and a Python driver. Each agent needs only a thin wrapper.

  • Instructions: one plain Markdown file, strategy/compiler/AGENT.md. It holds the compile contract (strategy file format §7)1 and the rules for unit files in this document. It names no feature that only one agent has.
  • Driver: pw.py strategy compile [--agent claude|codex] [--model M] [--full] [--milestone m1] --json. It runs prepare. Then it calls the agent headless for step 2 (claude -p or codex exec) with AGENT.md and the work order. Then it runs assemble, verify, and report, and it repeats the repair loop. It obeys the agent CLI contract of the lab (one JSON envelope, exit codes)13. Thus an autonomous loop can drive it.
  • The driver enforces the write scope, not the permission system of the agent. After the agent returns, the driver uses git to make sure that only files under strategy/compiled/<build-id>/units/ and the report draft changed. Any other change fails the build, and the driver reverts it. This operates the same for every agent.
  • Wrappers: a Claude Code subagent (.claude/agents/pw-compiler.md) and a lab skill (paintbot-pw-compile) for use in a Claude session. Codex gets the matching AGENTS.md pointer. Each wrapper only points to AGENT.md and the driver.
  • The build records the agent and the model. The compiler field of version.json records the agent (claude or codex), its CLI version, the model ID, and the hashes of AGENT.md and LESSONS.md. One config file sets a default agent and model. Thus builds are comparable, unless a person selects a different agent or model.
  • Memory: strategy/compiler/LESSONS.md, in the repo. It holds the BASIC pitfalls that the compiler learned. For example, NOT binds tighter than =, rnd is a reserved name, and division by zero disables the seat6. The agent reads the file on every run and can propose additions in its report. A person or the edit loop accepts an addition with a commit. The file is in the repo and not in personal memory, thus any agent reproduces the same build.
  • Context for each unit: the text of the component, its previous unit (if one exists), and the interfaces of the units that it uses (from map.json: globals and SUB signatures). It also gets the applicable policy-surface.md sections and LESSONS.md. It does not get the whole strategy file. This keeps the context small and the output focused.

10 · Incremental builds

  • A component is changed when the hash of the fields that the compiler reads is different.
  • A change to an interface also makes the dependent components again.
  • The deterministic parts are made again on every build, and unchanged input gives unchanged output.
  • prepare makes a hash of the normalized text of each component. The hash uses only the fields that the compiler reads: Spec, Params, Uses, Done when, Abort when, and Log. It does not use Rationale, Evidence, or Status. A component is changed when that hash is different from the hash in map.json.
  • The process also makes a component again when a component that it uses changed its interface (globals or SUB signature). prepare calculates this from map.json.
  • --full makes every unit again. Use it when the runtime skeleton changes or when drift accumulates.
  • Each build makes the rule tables, constants, and telemetry tables again. They are deterministic, thus unchanged input gives unchanged output.

12 · Alternatives considered

  • Seven alternatives lost.
  • The main reasons: exactness is cheap in Python, a change must stay local, v1 needs no custom harness, the compiler must not depend on one agent, and the local screen must not veto a behavior change.
AlternativeWhy not
Adopt a spec-driven toolkit (Spec Kit and similar)5The toolkits are for one-shot application features. They do not support incremental regeneration of one file under per-tick budgets.
The LLM compiles everything, rules and priorities tooIt is less reliable where exactness is cheap. The rule table must agree exactly with the rule selection that the audit does again.
One monolithic policy.bas that each build writes againLarge diffs with much noise. There is no guarantee that a change stays local.
A custom harness on the Claude Agent SDK or Codex SDKMore to make and maintain for v1. The headless modes of both CLIs, with a small Python script to drive them, already give the loop that we need.
A Claude-only subagent and skill as the driverThis ties the process to one agent. The Python driver is agent-neutral, and a loop can drive it.
The local screen as a blocking gate for every buildIt vetoes behavior changes on the judgment of a self-play opponent. A hosted A/B decides behavior changes (§8.2).
Builds kept out of gitWe lose the review diffs and the link from an uploaded policy to its exact file.

13 · Risks

  • The largest risk: BASIC that compiles but does not match the spec. G4 blocks only builds that are not intended to change behavior.
  • Three more risks: interface drift, budget creep, and local tools that lag the league.
Risk 1 · BASIC that compiles but does not match the spec The LLM can write BASIC that compiles but does not match the spec. G4 blocks only builds that are not intended to change behavior. Even then, it catches only gross regressions. Mitigations: small context for each unit, LESSONS.md, the five-level checks in telemetry, and hosted A/B for changes of behavior.
Risk 2 · Interface drift between units A unit changes a global that another unit reads. Mitigation: map.json records interfaces, and prepare makes the dependent units again.
Risk 3 · Budget creep Many small units can add up. G3 measures the whole file on every build.
Risk 4 · Local tools lag the league The gates operate against the pinned engine9. The pin must stay the same as the league build (pw.py deployed-ref).

14 · Decisions (2026-09-30)

  • Six decisions. Python makes all exact parts, builds go into git, and the process stops at the local gate.
  • The compiler is agent-neutral, and the local screen never vetoes a behavior change.
Decision 1 · What the LLM does not write

Python makes the rules, priorities, Adaptations (changes of priority), commitment, constants, telemetry tables, and header. A hand-written runtime library holds the skeleton, the telemetry print routines, and the comms codec, and the build copies it unchanged. The LLM does not make any of these.

Decision 2 · Builds in git

We commit builds to git.

Decision 3 · Build ID

The build ID is <source short SHA>-<n>.

Decision 4 · End of the process

The process stops at the local gate. Upload and A/B use the current skills with the build ID.

Decision 5 · Agent-neutral compiler

The compiler is agent-neutral. A Python driver calls Claude Code or Codex headless with one plain AGENT.md. The driver enforces the write scope itself, and it records the agent and the model. Each agent has a thin wrapper. The lessons file is in the repo. v1 has no custom harness.

Decision 6 · The local screen never vetoes a behavior change

The local screen never vetoes a behavior change. It blocks only builds that are not intended to change behavior, the M1 milestone, and any build with a bad seat.
