Kissinger: the webDiplomacy Gunboat Search Policy

How the champion policy for the webDiplomacy Coworld picks its orders: the components, the board evaluation, and the search, as deployed in webdip-dumbbot:v8 (submitted 2026-10-07).

Executive Summary

Kissinger plays classic seven-power Diplomacy in its gunboat form: no messages, and every power orders at the same time. It is not a separate program. It is the generic SearchBot with a single config override, OPP_MODEL_LEVEL=11. In every movement phase it samples what each opponent is likely to order, searches over its own orders for the plan with the best average outcome across those samples, and measures each outcome by actually adjudicating the combined orders and scoring the resulting board. Its one-line description is “assumes you are clever too: best-responds to opponents who best-respond.”

The search looks exactly one phase ahead (depth 1) and then applies a static evaluation. Longer-range intent lives inside that evaluation, in the positional term borrowed from DumbBot’s value map, not in deeper simulation. Every variant that searched harder or deeper was built, measured in paired games, and lost or tied. The lab’s own conclusion is that the evaluation, not the search, is now the bottleneck2.

1 · What Kissinger is

  • One personality of the generic SearchBot: the base search policy plus OPP_MODEL_LEVEL=1.
  • Strategy: a depth-1 best response against 16 sampled opponent order sets, scored by real adjudication plus a static evaluation.
  • Foresight beyond the current phase comes from the evaluation’s positional term, not from searching further ahead.

Every weight and switch in the bot is a flat module-level constant in one config module, and a personality is simply a base policy plus a set of overrides34. Kissinger is the search policy with one override: opponents are modelled at level 1, meaning each opponent is assumed to play a heuristic plan and then improve it by one round of its own best response1. The same container image hosts every personality, so switching between them is a configuration choice, not a rebuild.

The strategy fits in one sentence: for each movement phase, sample what every opponent is likely to order, search over our own orders for the plan with the best average outcome across those samples, and measure each outcome by adjudicating the combination and scoring the board that results. This is a one-phase-deep best-response search with a static evaluation. It is deliberately not a deep game-tree search: deeper lookahead variants exist in the code and are switched off, because they lost or tied in paired tests (§6).

2 · Architecture

  • A phase loop polls the server, builds a fresh policy object per phase with a deterministic seed, and saves the chosen orders.
  • Only movement phases are searched. Retreats and builds go straight to DumbBot.
  • DumbBot is reused four ways: it plays retreats and builds, seeds our search, is the base opponent model, and supplies the positional value map.

The phase loop polls the webDiplomacy server, reads the public board and variant files, and constructs a fresh policy object for each phase. That object gets a deterministic random-number generator seeded from the game seed, country, turn and phase. Every random choice in the decision draws from this one generator: DumbBot’s tie-breaking, the opponent samples, the competent-or-random draws, and the unit order in the ascent. As a result, a decision is exactly repeatable for a given game seed and phase. The loop calls choose(slots), saves the orders with Ready set, and then compares the saved orders with the requested ones, because the upstream server silently drops invalid orders. It finishes each phase by printing one JSON decision line with compute time, trace counters and the count of rejected orders. A state dictionary persists for the whole game and carries the opponent beliefs from phase to phase5.

SearchBot owns the decision state and dispatches by phase type6. A movement phase runs the full pipeline shown in Figure 1: build the board model, draw opponent samples, precompute the inputs for the fast adjudicator, and hand off to the move search.

DumbBot does a lot of work in this design. It plays every retreat and build phase (build search is off). It generates the 12 seed plans our search starts from. It is the base model of what each opponent will do. And its per-position value map is the positional term of the evaluation. When this document says “DumbBot”, it means this reimplementation, written against the webDip map graph after the MIT port.

3 · Board-state evaluation

  • A plan’s value is the mean, over 16 opponent samples, of the static score of the adjudicated board.
  • The static score is 10 per projected centre, plus a normalized positional term, minus 3 per dislodged unit of ours.
  • The positional term is DumbBot’s value map, which spreads centre values outward over the map. All foresight beyond this phase lives here.
  • The lab’s measured conclusion: this evaluation is the bottleneck, and more search over it does not help.

The evaluate loop

PositionEvaluator.evaluate(ours) converts our plan to compact orders once. Then, for each of the 16 opponent samples, it concatenates our units and orders with that sample’s, adjudicates the full set natively, and scores the resulting board with score_fast. The plan’s value is the mean over the samples10. A knob, SEARCH_RISK, can pull the aggregate toward the worst sample. Kissinger sets it to 0, so it uses the pure mean4.

The static score of one outcome

score_fast scores one adjudicated board from our side14:

score = 10 × projected_centres + 1 × positional − 3 × units_dislodged

Projected centres. For every supply centre, the holder is the unit standing on it after adjudication if there is one, and otherwise its current owner. We count the centres that would be ours. This answers “who would own each centre if this phase were autumn”, so even in spring the score rewards standing on centres.

Positional. For each of our surviving units, take DumbBot’s value for the node it ends on (a node is a unit type plus a territory), and divide by the largest node value on the board, vmax6. A unit on the best square therefore contributes about 1.0, and the whole term is small next to a single centre, which is worth 10. It works as a tie-breaker between plans that win the same centres, and it is the only carrier of longer-range intent.

Dislodged penalty. Each of our units that is dislodged costs 3. A dislodged unit no longer holds its province and must retreat or be disbanded.

The three weights (10, 1 and 3) are config constants4. A fallback scorer computes the same formula from the diplomacy package’s state for the rare orders the fast path cannot handle15.

What “positional” measures: the DumbBot value map

The value map is computed once per phase for each power7. It works in four steps.

1. Power sizes. Each power with n centres gets a size of n² + 4n + 16. Larger powers are both more threatening and more rewarding to attack.

2. Base value of each centre. A centre we do not own gets an attack value equal to its owner’s size. Unowned neutral centres count as one pseudo-power sized by how many neutrals remain. This is a deliberate departure from the MIT port, which gives neutrals 0. One of our own centres gets a defense value equal to the size of the largest enemy adjacent to it. A node’s base value is attack times the attack weight plus defense times the defense weight: 700 and 300 in spring, 600 and 400 in fall.

3. Proximity diffusion. Ten rounds of diffusion spread value outward from the centres. In each round, a node’s value becomes the best value in its own province plus the sum of the values of the nodes that can reach it, all divided by 5. Each round produces one proximity layer, so layer 0 is “value of being here” and higher layers are “value of being near something valuable”, decaying with distance.

4. Final node value. The ten layers are combined with season-specific weights, then adjusted for local force: plus 1000 times our strength (our units adjacent) and minus 1000 times the competition (the largest number of any one enemy’s units adjacent). Fall weights emphasize standing on a centre; spring weights emphasize standing one step away, ready to take it in autumn.

This is how a depth-1 search still “plans”. A spring move that ends a unit next to a weak power’s centre wins no centres this phase, but it scores higher on the positional term, so the search prefers it, and the autumn search can then take the centre.

Other evaluators in the same slot exist but are not used by Kissinger: a share objective (34 × SC² / ΣSC², the league’s draw score), a diplomacy adjustment that weights centre values by hostility, and a learned ridge-regression evaluator that predicts centres two years ahead (11 features, R² 0.752 on held-out data, trained on 37,025 rows). The learned evaluator is discussed in §6.

Known weakness: evaluation is the bottleneck The lab’s measured conclusion is that more search over this evaluation does not help and often hurts, most likely because a stronger search finds the evaluation’s errors and exploits them: the optimizer’s curse216. Three restarts, triple alternatives, more opponent samples and deeper rollouts all came out null or negative (§6). The next real gain probably needs a better evaluation, for example one trained causally from self-play outcomes.

4 · Search strategy

  • We search against 16 joint opponent samples, each one a set of orders for all six rivals.
  • Opponents are modelled as a competence-weighted mix of “DumbBot improved by one best-response pass” and uniformly random orders.
  • Our own plan starts from the best of 12 DumbBot seeds and climbs by first-improvement coordinate ascent over single, paired and convoy changes.
  • A fast adjudication path, with a convoy approximation and a native Nim resolver, keeps thousands of evaluations per decision affordable.

4a · The opponent model: what we search against

OpponentModel.sample builds a DumbBot for each opponent power, using that power’s own value map, and draws 16 joint samples8. For each sample and each opponent, it decides whether the opponent is acting competently this time. With probability sigmoid(log-odds) it is, and it gets a model plan. Otherwise it gets uniformly random legal orders. DumbBot itself is randomized, sometimes playing near-tied options17, so the 16 samples differ even for opponents believed to be fully competent.

Level 1, the Kissinger change. Each competent opponent’s DumbBot plan is improved by one pass of that opponent’s own single-unit best response18. For each of its units, in random order, the model tries every legal non-convoy order and keeps it if it raises the opponent’s score. That score uses the same score_fast formula, but from the opponent’s side and with its own value map, averaged over two contexts in which we and the other powers play DumbBot plans. In short, we assume each opponent is one step smarter than a heuristic, and no more. §6 shows that assuming less, assuming more, and mixing the two all lost.

Belief update between phases. update_beliefs reads the public history of the previous movement phase and updates each opponent’s competence log-odds, which start at 0 (a 50/50 prior) and are clipped to ±819. For each order the opponent actually gave:

  • Likelihood if competent = 0.5 × (the fraction of our stored DumbBot samples that matched the order) + (0.5 / the number of sensible orders, if the order is sensible; otherwise 0.02 / the number of legal orders).
  • Likelihood if random = 1 / the number of legal orders.
  • Log-odds increase by the log of the ratio.

An order is sensible if it is a hold, a plain move, or a support or convoy involving the power’s own units. Random players give themselves away by supporting or convoying other powers’ units. The choice of “sensible” as the test matters. An earlier version scored competence by “matches DumbBot”, which made every bot treat strong opponents that do not play like DumbBot as random. Fixing it was worth +0.106 score in paired games (z = 2.25)16. The same pass also updates a hostility memory, which only the diplomacy variant uses.

4b · Our move search

choose_movement runs five steps9.

1. Seeds. Generate 12 DumbBot plans for us, evaluate each across the 16 samples, and sort them20.

2. One restart. Only the best seed is optimized (SEARCH_RESTARTS=1). Three restarts lost to one in a championship test, another instance of the optimizer’s curse4.

3. Joint alternatives. For each of our units, build the list of changes to try21:

  • Singles: every legal non-convoy order for that unit alone.
  • Pairs: that unit’s move to X, plus another of our units supporting that move. A supported attack only pays when both orders change together. Changing one unit at a time can never find it, because the unsupported move or the idle support each scores worse on its own.
  • Convoys: an army’s convoyed move, plus the convoy orders of our fleets along the path, for the same reason.

Triples (a move plus two supports) are implemented but off.

4. Coordinate ascent. Run up to 6 passes. Each pass visits our units in random order and, for each unit, tries every joint alternative by evaluating the modified plan. Any strict improvement (greater than the best score plus 10−9) is accepted immediately. This is first-improvement hill climbing. The ascent stops when a full pass changes nothing, or when the time budget runs out22.

5. Finish. Return the best plan, with each order passed through DumbBot’s legality check, so an illegal order becomes a hold.

Two optional extras are off in Kissinger: softmax mixed selection among the top plans (the Rasputin personality) and a spring-to-autumn rollout re-rank (Napoleon).

4c · The fast path that makes it feasible

The search evaluates thousands of (plan × sample) boards per decision, so adjudication has to be cheap. Orders are converted to compact province-level tuples and resolved by a native Nim implementation of Hold, Move and Support, called through Nimpy, which returns for each unit whether it moved and whether it was dislodged1112. A Python reference adjudicator is kept only for verification, and the AGPL diplomacy package is the fallback for orders that cannot be converted.

Convoys are approximated. A convoying fleet is treated as holding, and a convoyed army move becomes a plain move if every fleet on its path is ordered to convoy exactly that move. Otherwise it becomes a hold. A fleet being dislodged and so disrupting the convoy is ignored11. Before this approximation, the package fallback took about 95% of decision time. With it, decisions became about 9× faster with no change in strength16. The Nim adjudicator in v8 cut a further 27% off the median, with bit-identical behaviour checked against a golden contract of 334 exact decisions23.

7 · Open questions and risks

  • The main open direction is a better evaluation. The remaining items are known approximations and untested ideas.
Open · Better evaluation The evaluation is the measured bottleneck. A position evaluation trained causally from self-play outcomes is the leading candidate. The learned ridge evaluator showed that predicting centres well (R² 0.75) is not enough if the search can exploit it.
Open · Diplomacy in the opponent model Diplomacy so far changes only centre values. Changing the opponent model itself, for example expecting peace from powers that have not been aggressive, is untested.
Open · Press variant If the league moves to a press (messaging) variant, an LLM press player becomes relevant.
Risk · Depth-1 horizon Tactics that need two phases, such as setting up a supported attack for next season, rely on the positional heuristic rather than on search.
Risk · Convoy approximation Ignoring convoy disruption is acceptable for scoring hypotheticals, but the evaluation is slightly wrong in convoy-heavy positions.
Risk · Determinism contract All components share one RNG, so the order of random draws affects decisions. Any change that adds, removes or reorders a draw changes behaviour, even if the logic is otherwise identical3.
