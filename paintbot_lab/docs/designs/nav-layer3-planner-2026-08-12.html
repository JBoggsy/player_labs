Design proposal · 2026-08-12 · PROPOSAL — awaiting ruling

Layer 3 — the planner

Weighted A* as the single navigation search for the stencil nav rework — a worked proposal argued from the Phase 0 benchmark, for James's ruling before v65 implementation begins.

Executive Summary

The stencil navigation rework replaces today's two planners — goal-anchored Dijkstra flow fields followed one 8 px hop at a time, plus a per-agent cached A* on the eroded 8 px grid — with one weighted A*-family search that all navigation eventually routes through. This proposal specifies that planner. The Phase 0 benchmark ran weighted A* on the real competition maps from the v62–v64 hosted batches, with synthetic danger blooms deliberately chosen to weaken the heuristic, and the headline result is that a flat (non-hierarchical) search on a 4 px lattice with exact supercover edge checks clears the budget comfortably: typical replans run 1–12 ms against a ~41 ms tick, and the worst single measured replan at the chosen configuration is 47 ms — a rare one-tick-ish blip on the giant probe map, with a shelved inflation valve (w = 1.3) that cuts it roughly 30× if hosted reality ever demands it.

The most consequential choices: no hierarchy (D1), pixel-exact edges by construction (D3), a Dijkstra-oracle heuristic for stable goals that carries a real admissibility caveat bounded by property tests rather than assumed away (D4), optimal search by default with inflation as a config knob (D5), and a deliberately narrow v65 ship scope — swap only the existing A* consumers, leave flow-following to Layer 4 — so the matched hosted batch stays readable (D8). Even so, the v65 behavior delta is broad: every A*-reason route can change shape. Four points await James's ruling (P1–P4).

1 · Problem & Context

  • Two planners today (flow fields + cached 8 px A*) collapse into one weighted A*-family search; route quality becomes cost terms, not steering hacks.
  • Layers 1–2 are shipped and hosted-validated, and two performance landmines were already cleared en route — Layer 3 inherits both as satisfied hard requirements.
  • Layer 3 ships the planner itself; the full kill of flow-following and beelines is Layer 4's Intent contract.

The governing document for this work is the nav rework sketch docs/designs/nav-rework-sketch-2026-08-11.md §3.3. Today the agent navigates with two separate planners: goal-anchored Dijkstra flow fields followed one 8 px hop at a time, and a per-agent cached A* on the eroded 8 px grid nav.nim:22-87. The rework replaces both with one weighted A*-family search that all navigation eventually routes through, so that route quality — danger, cover exposure, terrain — becomes cost terms in that one search instead of per-objective steering hacks scattered across dispatch code.

The layers already shipped and hosted-validated set the stage: Layer 1 delivered the exact L∞ clearance field (canStand at worldmap.nim:233, supercover segmentClear at worldmap.nim:262); Layer 2 delivered components, rooms, chokes, and cover (v62); post re-sourcing and belief-scored facing landed in v63, and the wide post pool in v64. Two performance landmines were cleared along the way, and Layer 3 inherits them as hard requirements already satisfied: fieldsFor now returns lent RouteFields worldmap.nim:86,675, ending the ~1.4 MB per-call field copies; and the argument-order rule that the routeDistance/distanceAt GOAL slot takes stable goals only — the goal keys the lazy Dijkstra cache, and arbitrary goals were each minting a full-grid field until that detonated and was fixed in v64.

Today's A* is exactly what the rework exists to kill: it plans on the 8 px grid, snaps endpoints via nearestWalkable with an up-left bias, and when the goal is unroutable it returns the raw goal and the agent beelines nav.nim:66-87. This proposal ships the planner itself; the full kill of flow-following, the seven reason-string dispatch lists, and the beelines is Layer 4's Intent contract.

2 · Phase 0 Benchmark — the Evidence

  • Weighted A* was benchmarked on the REAL competition maps from the v62–v64 hosted batches, with synthetic danger blooms chosen to weaken the heuristic — the worst case for A*.
  • At the chosen config (4 px, exact edges, w = 1.0) typical replans are 1–12 ms; worst measured single replan is 47 ms against a ~41 ms tick.
  • Exact supercover edges cost +40–70% over endpoint-only checks; memory is 13 MB per process at 4 px on the giant map; zero unroutable results in any class.

The scratchpad harness (layer3_bench.nim, from the Layer 2 scratchpad) ran weighted A* on the real competition maps from the v62–v64 hosted batches, using clearance fields logged by the agent and decoded offline: the h2h cell (1235×659 px), the 4-team ffa cell (1728×1728 px), and the giant probe map (3211×1713 px). Danger was emulated with 8 synthetic believed-track blooms (radius 150 px, peak +3.0 additive cost multiplier) — deliberately weakening the heuristic, which is the worst case for A*. Edge validity "exact" means a supercover canStand DDA per edge (the same primitive as segmentClear); "endpt" means endpoint canStand only. Each class ran 25 queries, shared across configurations. Machine: M4 Pro, single process — hosted runs 16 processes, but replans are occasional, not synchronized.

Supporting numbers. Exact versus endpoint-only edge checks costs +40–70% time (giant 4 px arbitrary: 12.00 vs 6.92 ms mean) — affordable, and what it buys is argued in D3. Memory for the generation-stamped node arrays (gScore/cameFrom/closed/gen, no per-query clearing) is 13 MB at 4 px on the giant map and 52 MB at 2 px. There were zero unroutable results in any class — all sampled starts and goals were standable; preventing component-mismatched goals is Layer 4's contract.

Budget context: the game runs 24 ticks/s (~41 ms per tick). Replans are per-agent and occasional — goal moved, stuck watchdog, or a cadence for moving targets — so the realistic worst load is a handful of replans per second across 8 agents, not per-tick-per-agent. The worst single measured replan at the chosen configuration (4 px, exact edges, w = 1.0) is 47 ms (giant map, arbitrary goal, euclid) — a rare worst-case blip, one-tick-ish, and the inflation valve cuts it ~30× if that is ever needed hosted.

3 · Decisions D1–D8

  • Every decision below cites the Phase 0 matrix; none rests on intuition alone.
  • The riskiest call is D4's Dijkstra oracle — its admissibility caveat is real and gets bounded by property tests, not assumed away.
  • D8 keeps the v65 diff to one change class: swap the A* consumers, leave flow-following alone.
Decision D1 · Architecture

Flat weighted A*; no hierarchy. The worst measured configuration at 4 px is 47 ms on the giant map; typical replans are 1–12 ms. A hierarchical planner (PoI graph at the top level plus local refinement) would add an abstraction layer, path-stitching artifacts, and a second thing to test — to solve a budget problem that does not exist. The PoI graph (rooms and chokes, from v62) stays available as a fallback if hosted reality contradicts the bench. This answers sketch Q1 by measurement.

Decision D2 · Lattice step

4 px lattice step by default. It is 3–4× cheaper than 2 px everywhere in the matrix, and validity stays pixel-exact at any step because node and edge admission read the clearance field (canStand) — the step only quantizes where waypoints may land, and the Layer 5 follower smooths waypoint placement anyway. This is not a return to the old 8 px coarsening problem: the old grid was the walkability truth (conservative, with a biased snap); here the lattice is only waypoint placement. 2 px stays available as a config knob (STENCIL_PLAN_STEP_PX) for experiments.

Decision D3 · Edge validity

Exact supercover edges. Every edge is admitted via the supercover canStand DDA — the same primitive as segmentClear — so every returned path is engine-walkable by construction: no post-validation pass, and no reliance on engine wall-slide to survive route corners. (Slide remains a bonus for micro, per the v60/v61 wall-slide lesson, not a route crutch.) The measured cost is +40–70% over endpoint-only checks — affordable, and it buys away an entire class of "path clips a corner" bugs.

Decision D4 · Heuristic

Euclidean always; Dijkstra oracle for stable goals. For goals in the stable set — team homes and the own capture point, the fields minted at init — the heuristic is h = max(euclid, gridDistance × 0.999). Measured effect: a 2–4× expansion reduction (giant stable at w = 1.0: 27,592 → 9,681 expansions).

The ×0.999 clamp addresses a real admissibility caveat, stated plainly: the 8 px-grid Dijkstra distance can in principle exceed the true 4 px-lattice distance where the conservative grid misses sub-cell passages, which would make the oracle inadmissible at the margin. Phase 0 observed zero anomalies, but v65's property tests bound the actual path-cost deviation against an exact-euclid reference search on random maps rather than assuming the caveat away. If deviation shows up, the clamp factor drops — turning the oracle into a slightly weaker but safe bound. Arbitrary goals (pursuit, interception, evacuation) use euclid: they have no minted field and must not mint one — that is the v64 rule.

Decision D5 · Inflation weight

w = 1.0 (optimal) by default; inflation is a shelved valve, not a default. w = 1.3 collapses worst cases ~10–30× (giant arbitrary: 46.68 → 1.44 ms worst) with bounded suboptimality ≤30%, but the budget does not require it, and optimal paths make behavior more predictable and debuggable. The knob STENCIL_PLAN_WEIGHT ships (default 1.0), so a hosted timing surprise is a config flip, not a code change.

Decision D6 · Cost function v1

Per-edge cost = octile base length × terrain × (1 + soft penalties). The terms:

  • Terrain: trench ×5, matching engine climb-out speed (sketch §3.3); active puddles when GV41 activates them (bounding-box labels, loose — a cost, not a wall). Barriers, trenches, and puddles never become walls — they do not block movement.
  • Danger: an additive bloom per believed enemy track (velocity-projected, fresh within TrackTtlTicks — the same input as v63's facingScore): radius 150 px, linear falloff, peak weight set per profile. This is not the unvalidated belief.danger grid — the sketch keeps that out of cost functions pending its validation experiment.
  • Exposure: at each node, if the cell's coverDirs mask leaves the node uncovered from the bearing toward any fresh believed track within gun range, add the exposure weight (per profile). Cheap: one bitmask test per fresh track per expanded node, reusing v63's facingScore machinery worldmap.nim:583.
  • Cohesion: deferred — the sketch marks it optional, and adding it in v1 would muddy attribution.

Draft profile weights (sketch Q2: start with exactly three) — default: danger 0.5, exposure 0.25; carrier: danger 2.0, exposure 1.0 (evade — the "carry_home should evade" requirement lands here); hunter: danger 0.1, exposure 0.1 (close distance, accept risk). Profiles are weight bundles on the future Intent (Layer 4); in v65 all swapped consumers run the default profile (see D8).

Decision D7 · Replan policy

Plain re-search, no D*-lite (sketch Q3). Each agent caches its path and invalidates when (a) the goal moved more than the ReplanGoalCells equivalent (existing knob, config.nim:118, 2 cells = 16 px), (b) the stuck watchdog fires (existing progress test), or (c) the moving-target cadence triggers: every 12 ticks (0.5 s) for pursuit- and interception-class goals. At ~1–12 ms per replan, incremental replanning is complexity without payoff. The cadence ships as a knob, STENCIL_PLAN_MOVING_REPLAN_TICKS (default 12).

Decision D8 · v65 ship scope

Swap the A* consumers only; flow-following waits for Layer 4. The new planner replaces astarWaypoint for its current reason set (intercept_thief, clear_grenade, rejoin, escort_carrier, fetch_*, convert_hunt, squad_move/watch/hold, hunt_fallback), returning the same waypoint contract to the existing follower. FlowReasons (carry_home, steal, to_hold, to_post, early_defense, barrage_center) keep flow fields until the Layer 4 Intent contract lands — killing both dispatch paths simultaneously with a new search would make the matched batch unreadable, and one change class per version is the lab's standing discipline. The unroutable-goal beeline fallback in nav.nim:77-79 survives v65: goals are not yet validated — that contract is Layer 4's — and the planner logs unroutable requests to trace so Layer 4 has data.

4 · Alternatives Considered

  • Each rejected option lost to a measured number or a standing rule, not to taste.
  • Hierarchy and inflation stay on the shelf as contingencies rather than defaults.

JPS / JPS+. Jump-point search requires uniform costs, and the cost terms are the entire point of the rework. The sketch already ruled it out; re-affirmed here.

Hierarchical A* now. The bench says flat search clears the budget with a 3–30× margin. Hierarchy is the contingency (D1), not the plan.

2 px default step. 3–4× the cost, for waypoint granularity the follower does not need. Revisit only if Layer 5 micro wants finer waypoints in tight play.

Endpoint-only edge checks. 40–70% cheaper, but reintroduces corner-clipping paths that only engine slide bails out — contradicting the sketch's §2 goal of pixel-exact correctness everywhere.

D*-lite / incremental replanning. Replans cost 1–12 ms; incremental search's bookkeeping complexity buys nothing at this scale.

Inflation by default (w > 1). Not needed for budget, and suboptimal paths are harder to reason about in trace diffs.

Danger from the belief.danger grid. Its semantics are unvalidated (the sketch's Q10 experiment is still open); believed tracks are the direct, interpretable source.

5 · Validation Plan (v65)

  • Property tests bound the D4 oracle caveat empirically instead of trusting Phase 0's zero-anomaly run.
  • Corpus timing plus trace keys give Layer 4 its data feed; the hosted batch is the standard matched shape.

Property tests (scratchpad harness, house method): every returned path edge passes segmentClear — true by construction, so the test guards regressions; path cost stays within bound of a brute-force reference search on random small maps, which bounds the oracle-admissibility caveat from D4; determinism; and no-path if and only if BFS says the components are disconnected.

Corpus timing: the plan_ms distribution on the three batch maps plus the 4ffa8 giant, with trace keys plan_ms, plan_expansions, plan_cache_hits, and plan_unroutable — the last being Layer 4's data feed.

Viewer: a path debug layer in render_topology.py — click start and goal, see the planned route plus the expanded-region heatmap, produced by the real production search via the harness (the same drift-guard pattern as selection).

Hosted: a matched v65-vs-v64 batch in the standard shape — 12 requests / 58 episodes, re-resolved board, paired giant probes.

6 · Open Questions P1–P4

  • These four points are what this proposal asks James to rule on; everything else is decided above, pending that ruling.
P1 · Danger bloom shape Radius 150 px, linear falloff, profile-weighted peak: fine as v1, or a different shape/radius?
P2 · Exposure term in v1 Include the exposure term in v1 at all, or defer it to Layer 4 with the profiles? (v65 runs the default profile only; danger + exposure still shape default routes.) Lean: keep both terms in v1 at default weights, so the cost machinery is exercised before profiles multiply.
P3 · Moving-target replan cadence 12 ticks (0.5 s) — accept, or tune later? The knob (STENCIL_PLAN_MOVING_REPLAN_TICKS) ships regardless.
P4 · Viewer path layer scope In v65 scope, or split out to keep the diff smaller? Lean: in scope — it is the inspection tool for every later layer.

7 · Risks

  • The two watch-items are the oracle's admissibility margin and cost-term triple-counting; both have concrete mitigations in v65.
  • The v65 batch's behavior delta is broad by design — the expected-delta list is written down in advance so the matched batch stays interpretable.
Risk · Oracle inadmissibility at the margin The D4 caveat: the 8 px-grid Dijkstra distance can in principle exceed the true 4 px-lattice distance. Bounded by v65's property tests; the mitigation is lowering the ×0.999 clamp.
Risk · Cost-term interactions Danger + exposure + terrain can triple-count near walls where tracks cluster. v65 traces per-term totals per path, so the matched batch's behavior diffs can attribute route changes to specific terms.
Risk · Per-process memory Per-search arrays are per-process: 13 MB on the giant map at 4 px × 16 processes ≈ 200 MB aggregate on one host. Acceptable — hosted runners are per-seat containers — but noted for the record.
Risk · Broad v65 behavior delta Every A*-reason route can change shape in the v65 batch. Expected-delta list, stated in advance: route geometry for the ~10 swapped reasons, danger-avoiding detours near believed enemies, and no change to flow-reason movement.
